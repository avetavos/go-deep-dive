## การจัดการ Error ใน Go

ภาษาส่วนใหญ่จัดการกับความล้มเหลวผ่าน exceptions — กลไกพิเศษที่ควบคุมการไหลของโปรแกรมโดยการ unwind call stack จนกว่า `catch` block จะดักจับปัญหาไว้ได้ Go เลือกแนวทางที่แตกต่างอย่างสิ้นเชิง: **errors คือค่าธรรมดา** ที่คืนกลับมาพร้อมกับผลลัพธ์และตรวจสอบตรง ๆ ด้วย `if err != nil` ไม่มี hidden control flow และไม่มี unchecked exceptions — ทุก failure point มองเห็นได้ที่ callsite บทเรียนถัดไป Error Values จะครอบคลุม interface `error` และ pattern นี้แบบละเอียด

ครึ่งหลังของโมดูลนี้คือเครื่องมือคนละแบบไปเลย: **generics** ให้ function หรือ type เดียวทำงานกับหลาย concrete type ได้ โดยตรวจสอบตอน compile time แทนที่จะเขียนซ้ำด้วยมือหรือ type assert ตอน runtime panic และ recover อยู่ตรงกลาง — เป็นทางออกฉุกเฉินสำหรับ programmer error และสถานะที่เป็นไปไม่ได้ ไม่ใช่ตัวแทนของการคืน `(T, error)`

สิ่งหนึ่งที่ควรพกติดตัวมาจาก Functions ก่อนไปถึง Panic & Recover: deferred call ทำงานเป็น **LIFO order** — `defer` ตัวสุดท้ายที่ลงทะเบียนไว้ทำงานก่อน กฎนี้ไม่เปลี่ยนระหว่าง panic เลย และนั่นคือเหตุผลที่ `recover()` ต้องอยู่ข้างใน deferred function ตั้งแต่แรก

ทุกกฎในโมดูลนี้ลงเอยที่สิ่งใดสิ่งหนึ่งจากไม่กี่อย่างตอนเขียนโค้ดจริง: nil check ที่ทำงานทั้งที่ไม่ควร, compiler error ที่ระบุ pointer ที่ขาดหรือ constraint ที่ไม่ผ่าน, หรือ panic message ที่บอกตรง ๆ ว่าอะไรผิดพลาด การฝึกอ่านข้อความจริง ไม่ใช่แค่จำกฎแบบนามธรรม คือทักษะจริงที่โมดูลนี้สร้างขึ้น

## ตัวอย่างแรก

function เล็ก ๆ ที่คืนค่า `(string, error)` เพื่อแสดงรูปแบบพื้นฐานของการจัดการ error ใน Go:

export const firstLookCode = `package main

import (
\t"errors"
\t"fmt"
)

func greet(name string) (string, error) {
\tif name == "" {
\t\treturn "", errors.New("name must not be empty")
\t}
\treturn fmt.Sprintf("Hello, %s!", name), nil
}

func main() {
\tmsg, err := greet("Gopher")
\tif err != nil {
\t\tfmt.Println("error:", err)
\t\treturn
\t}
\tfmt.Println(msg) // Hello, Gopher!

\t_, err = greet("")
\tif err != nil {
\t\tfmt.Println("error:", err) // error: name must not be empty
\t}
}`;

`errors.New` สร้าง error value ธรรมดาจาก string คงที่ function คืนค่า `nil` เป็น error ในเส้นทางปกติ และคืนค่า error ที่ไม่ใช่ nil ในเส้นทางที่ล้มเหลว caller ตรวจสอบ `if err != nil` ทันทีหลังการเรียก — นี่คือ idiom ที่คุณจะเขียนนับร้อยครั้งใน Go

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| explicit error handling | ทุก failure point มองเห็นได้ชัดเจนใน code | verbose กว่า try/catch |
| error as value (not exception) | composable, predictable control flow | caller ต้องตรวจ error ทุกครั้ง |
| generics (Go 1.18+) | type-safe reuse, ไม่ต้อง `interface{}` | compile time เพิ่ม, syntax ซับซ้อนกว่า |
| panic/recover | abort ทันทีเมื่อ invariant ถูกละเมิด | ไม่ใช่ error handling ทั่วไป |

## ความเข้าใจผิดที่พบบ่อย

- **error handling ใน Go verbose เกินไป** — verbosity นี้ตั้งใจ: ทุก failure path มองเห็นได้ในโค้ด ไม่มี hidden exception
- **panic = exception ที่ควรใช้แทน return error** — panic ใช้สำหรับ programmer error เท่านั้น ไม่ใช่ expected failure
- **generics ทำ code ช้าลง** — Go generics ใช้ GC-shape stenciling: type ที่มี pointer/interface shape เดียวกันแชร์ instantiation เดียวกันและใช้ dictionary ส่ง type info ตอน runtime กรณีนี้ generics อาจ**ช้ากว่า** interface ด้วยซ้ำ; ส่วน value type (`int`, struct) ได้ code เฉพาะของตัวเองต่อ type จึงเร็ว

## อ่านโค้ดที่ AI เขียน

ทุกบทเรียนในโมดูลนี้ใช้การตรวจสอบชุดเดียวกันเพื่อจับ bug จากโค้ดที่ generate มาก่อนจะเอาไปใช้จริง:

- function คืนตัวแปร pointer แบบมี type ตรง ๆ ผ่าน result ที่เป็น `error` แทนที่จะคืน `nil` เปล่า ๆ ในเส้นทางสำเร็จหรือเปล่า? นั่นคือกับดัก typed-nil interface และ `err == nil` จะผิด
- `errors.As` ถูกเรียกด้วยตัวแปร target เองแทนที่จะเป็น address ของมัน (`&target`) หรือเปล่า? รูปแบบแรก panic ไม่ใช่แค่คืน `false`
- `recover()` ถูกเรียกข้างใน helper function ที่ deferred function เรียกอีกที แทนที่จะเรียกตรง ๆ ข้างใน body ของ `defer func() { ... }()` หรือเปล่า? แค่ระดับความห่างชั้นเดียวก็เพียงพอที่จะทำให้มันคืน `nil` เสมอ
- constraint interface (ที่มี type term คั่นด้วย `|` หรือ `~`) ถูกใช้เป็น type ของตัวแปรธรรมดา แทนที่จะใช้แค่ข้างใน `[T Constraint]` หรือเปล่า?
- โค้ดเรียก `sort.Strings` หรือคล้ายกันตรง ๆ กับผลลัพธ์ของ `maps.Keys` หรือเปล่า? ตั้งแต่ Go 1.23 มันคืน `iter.Seq` ไม่ใช่ slice และ compile ไม่ผ่าน
