## interface error

type `error` ของ Go คือ interface ที่เรียบง่ายที่สุดใน standard library:

```go
type error interface {
    Error() string
}
```

type ใดก็ตามที่ implement method เดียว — `Error() string` — จะ satisfy interface นี้และสามารถใช้ได้ทุกที่ที่ต้องการ `error` ค่า `nil` เป็น `error` ที่ถูกต้องและหมายถึง "ไม่มี error เกิดขึ้น" โดยสากล ไม่มีอะไรพิเศษเกี่ยวกับ type `error` ในระดับภาษา เป็นแค่ interface ธรรมดาที่ predeclare ไว้ล่วงหน้าเท่านั้น

## การคืนค่า error จาก function

convention แบบ idiomatic ของ Go คือการคืนค่า `(T, error)` เป็นสองค่าสุดท้ายจาก function ที่อาจล้มเหลวได้ caller รับทั้งคู่เสมอและต้องตรวจสอบ error ก่อนที่จะเชื่อถือผลลัพธ์:

```go
result, err := riskyOperation()
if err != nil {
    // do not use result — it is meaningless
    return fmt.Errorf("riskyOperation: %w", err)
}
// err is nil: result is valid
```

`%w` รักษา chain ไว้ให้ caller ยังตรวจสอบ error เดิมด้วย `errors.Is`/`errors.As` ได้ — จะกล่าวถึงในบทเรียนถัดไป

การคืนค่า error ให้ caller เป็นบรรทัดฐาน การกลืน error อย่างเงียบ ๆ — ละเว้น `err` ด้วย `_` — ควรทำอย่างตั้งใจและเกิดขึ้นน้อยมาก ใช้เฉพาะในกรณีที่ความล้มเหลวไม่มีผลจริง ๆ (เช่น การปิดไฟล์แบบ read-only หลังจากอ่านข้อมูลทั้งหมดสำเร็จแล้ว)

## การสร้าง error

Go มีสองวิธีมาตรฐานในการสร้าง error value ใหม่:

**`errors.New`** สร้าง error จาก string คงที่ ใช้เมื่อข้อความไม่เคยเปลี่ยนแปลง:

```go
var errTimeout = errors.New("operation timed out")
```

**`fmt.Errorf`** สร้างข้อความ error แบบ formatted ใช้เมื่อต้องการรวม runtime values เช่น ชื่อ, key หรือจำนวน:

```go
err := fmt.Errorf("user %d not found in database %q", userID, dbName)
```

หมายเหตุ: `%v` format ค่าแบบ inline และไม่แนบ wrapping metadata การ wrap — ใช้ `%w` เพื่อเชื่อม error ต่อกันเพื่อให้ `errors.Is` และ `errors.As` สามารถ unwrap chain ได้ — จะกล่าวถึงในบทเรียนถัดไป

## Sentinel errors

**sentinel error** คือตัวแปรระดับ package ที่แทนเงื่อนไขความล้มเหลวเฉพาะที่รู้จักกันดี:

```go
var ErrNotFound  = errors.New("not found")
var ErrPermission = errors.New("permission denied")
```

การประกาศ sentinel ในระดับ package ให้ caller ทดสอบด้วย identity ใช้ `errors.Is` แทน `==` เพื่อให้การตรวจสอบยังทำงานได้แม้ว่า error จะถูก wrap ด้วย context เพิ่มเติม:

```go
if errors.Is(err, ErrNotFound) {
    // handle the not-found case
}
```

Sentinel เหมาะที่สุดสำหรับเงื่อนไขที่ caller ต้องการ branch แยกทาง หลีกเลี่ยงการสร้าง sentinel สำหรับทุกความล้มเหลวที่เป็นไปได้ — ใช้เฉพาะสำหรับ error ที่ caller จัดการแตกต่างจากกรณีล้มเหลวทั่วไปอย่างแท้จริง

## รูปแบบ if err != nil

การตรวจสอบ `if err != nil` อย่างชัดเจนอาจดูซ้ำซากในตอนแรก แต่ออกแบบมาอย่างตั้งใจ Go ถือว่าทุกความล้มเหลวเป็นจุดตัดสินใจ: คุณต้องเลือกว่าจะ propagate error, wrap พร้อม context, retry, fallback ไปยังค่า default หรือ log แล้วดำเนินต่อ ภาษาไม่ได้ตัดสินใจแทนคุณ

วินัยนี้ทำให้โค้ดมองเห็นทุก call ที่อาจเกิด error ได้ที่ callsite เมื่ออ่าน function ของ Go คุณจะเห็นชัดเจนว่า operation ใดที่อาจล้มเหลวได้และ caller ทำอะไรกับแต่ละกรณี — ไม่มีการ propagate แบบ implicit ไม่มีเส้นทาง exception ที่มองไม่เห็น

## กับดัก typed-nil interface

ค่า `error` เป็น interface: คู่ (type, value) มันจะเป็น `nil` ก็ต่อเมื่อ**ทั้งคู่**ทั้ง type และ value ไม่ได้ถูกกำหนดเท่านั้น สิ่งนี้กลายเป็นกับดักทันทีที่ function ประกาศตัวแปร pointer แบบมี type แล้วคืนค่ามันตรง ๆ แทนที่จะคืน `nil` เปล่า ๆ:

```go
type MyError struct{ msg string }

func (e *MyError) Error() string { return e.msg }

func mightFail(fail bool) error {
	var e *MyError // nil *MyError
	if fail {
		e = &MyError{msg: "boom"}
	}
	return e // BUG: always a non-nil error interface, even when e is nil
}
```

`mightFail(false)` คืน `error` ที่มี type เป็น `*MyError` และมี value เป็น `nil` — นั่นคือ interface ที่ไม่ nil ที่ถือ pointer เป็น nil อยู่ข้างใน ไม่ใช่ nil interface `err == nil` จะได้ **false**:

## Shadowing err และจัดการทีเดียวจบ

`:=` จะประกาศตัวแปร**ใหม่**ทุกครั้งที่มีชื่ออย่างน้อยหนึ่งชื่อทางซ้ายที่ยังไม่เคยมีมาก่อน — รวมถึงใน init clause ของ `if` ด้วย นี่เป็นสาเหตุที่พบบ่อยของการทำ error หายไปเงียบ ๆ:

```go
func run() error {
	var err error
	if v, err := step(); err != nil { // BUG: := creates a new inner err
		fmt.Println("inner saw:", v, err)
	}
	return err // always nil here, even though step() failed
}
```

การรันโค้ดนี้จะพิมพ์ `inner saw: 0 step failed` ตามด้วย `run() returned: <nil>` — `err` ตัวนอกไม่เคยถูกแตะต้องเลย เพราะ `if v, err := step(); ...` ทำให้เกิด shadow ด้วยตัวแปรที่ scope อยู่แค่ใน block นั้น `go vet` ไม่จับ shadowing แบบนี้ (analyzer ชื่อ `shadow` เป็นเครื่องมือแยกต่างหาก ไม่ได้เปิดใช้เป็น default) การตรวจทุก `:=` ที่อยู่ใน `if`/`for` ข้าง ๆ `err` ที่มีอยู่แล้วใน scope จึงเป็นนิสัยที่ต้องรักษาไว้ด้วยตัวเอง

วินัยที่เกี่ยวข้องกันคือการ**จัดการทุก error แค่ครั้งเดียว** เลือกอย่างใดอย่างหนึ่ง: return มัน (จะ wrap ก่อนก็ได้), log มัน, หรือ recover จากมัน — ห้ามทำมากกว่าหนึ่งอย่าง และห้ามทำน้อยกว่านั้น การทั้ง log *และ* return error ตัวเดียวกันจะทำให้เกิด log ซ้ำซ้อนขึ้นไปตาม call stack ส่วนการไม่ทำอะไรเลยก็ทำให้ความล้มเหลวจริงหายไปเงียบ ๆ

## err == io.EOF ยังถือว่า idiomatic

`errors.Is` เป็นเครื่องมือเอนกประสงค์สำหรับเทียบ sentinel เพราะมันรอดจากการ wrap ได้ `io.EOF` เป็นข้อยกเว้นที่ตั้งใจและมีเอกสารรองรับชัดเจน: contract ของ `io.Reader` รับประกันว่า `io.EOF` จะถูกคืนตรง ๆ ไม่ถูก wrap เลย ดังนั้นโค้ดเก่า ๆ จึงยังเทียบมันตรง ๆ ได้:

```go
n, err := r.Read(buf)
if err == io.EOF {
	// end of stream, not a failure
}
```

`errors.Is(err, io.EOF)` ก็ใช้ได้เช่นกันและไม่เคยผิดเลย — แนะนำให้ใช้ในโค้ดใหม่เพื่อความสม่ำเสมอกับการเช็ก sentinel อื่น ๆ ทั้งหมด — แต่ก็ไม่ต้องแปลกใจถ้าเห็น `== io.EOF` ในโค้ดที่ใกล้ชิดกับ stdlib มันไม่ใช่ bug

## Behaviour interfaces

**behaviour interface** (เรียกอีกอย่างว่า opaque error check) ให้ caller ถามได้ว่า "error นี้ทำ X ได้ไหม?" โดยไม่ต้องรู้ concrete type ของมัน — มีประโยชน์เมื่อ error type ที่ไม่เกี่ยวข้องกันหลายตัวจาก package ต่างกันสามารถตอบคำถามเดียวกันได้ทั้งหมด:

```go
// timeout is a behaviour interface: any error that can answer "was this a
// timeout?" satisfies it, regardless of its concrete type or package.
type timeout interface {
	Timeout() bool
}

func isTimeout(err error) bool {
	var t timeout
	return errors.As(err, &t) && t.Timeout()
}
```

`errors.As` จะเดินไปตาม chain มองหาอะไรก็ตามที่ implement interface `timeout` — ไม่ใช่ type ที่เจาะจง นี่คือวิธีที่ `Timeout() bool` ของ `net.Error` ถูกออกแบบมาให้ใช้: error type ต่าง ๆ มากมายทั้งใน standard library และ third-party code implement มันไว้ caller จึงเช็กที่ behaviour ไม่ใช่ type

## อ่านโค้ดที่ AI เขียน

เมื่อโค้ดที่ AI generate return หรือเช็ก error ให้มองหาสิ่งเหล่านี้ก่อนเชื่อมัน:

- function ที่ประกาศตัวแปร pointer แบบมี type (`var e *MyError`) เคย `return e` ตรง ๆ ในเส้นทางที่สำเร็จหรือเปล่า แทนที่จะ return `nil` เปล่า ๆ? นั่นคือกับดัก typed-nil ด้านบน
- การเทียบ sentinel ใช้ `==` ทั้งที่ error อาจผ่าน `fmt.Errorf("...: %w", err)` มาจากที่ไหนสักแห่งใน call chain ก่อนหน้าหรือเปล่า? `==` จะพังทันทีที่มี wrapper เข้ามา ส่วน `errors.Is` ไม่พัง
- `err` ถูกประกาศซ้ำด้วย `:=` ข้างใน `if`/`for` ที่มี `err` อยู่ใน scope อยู่แล้วหรือเปล่า? เช็กดูว่า `err` ตัวนอกถูกอ่านค่าจริงในภายหลังหรือไม่
- ทุก error ถูกจัดการแค่ครั้งเดียวหรือเปล่า? สังเกต `log.Println(err)` ที่ตามด้วย `return err` ทันทีใน function เดียวกัน — นั่นคือการ log ความล้มเหลวเดียวกันซ้ำสองครั้งขณะที่มัน propagate ขึ้นไปตาม stack
- การเช็ก behaviour ใช้ type assertion ตรง ๆ (`err.(timeout)`) แทนที่จะใช้ `errors.As(err, &t)` หรือเปล่า? type assertion จะพลาด interface นั้นทันทีที่ error ถูก wrap แม้แต่ครั้งเดียว

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| error interface (1 method) | implement ง่าย, compose ได้ | ไม่มี stack trace โดยตรง |
| errors.Is() | match sentinel ใน chain ลึกแค่ไหนก็ได้ | ต้อง wrap error ด้วย %w ให้ถูกต้องก่อน |
| errors.As() | extract concrete error type พร้อม field | target ต้องเป็น pointer ไปยัง type ของ error (`&ve` เมื่อ `ve *VErr`) ถ้าไม่ใช่ panic ตอน runtime |
| sentinel errors | เปรียบเทียบง่าย, self-documenting | เป็น public API — refactor ยากถ้า name ต้องเปลี่ยน |

## ความเข้าใจผิดที่พบบ่อย

- **return nil error หมายถึง function สำเร็จเสมอ** — ถ้า caller ละเว้น error ด้วย `_` โดยไม่ตั้งใจ error ถูก ignore โดยสมบูรณ์
- **errors.New() และ fmt.Errorf() เหมือนกัน** — fmt.Errorf กับ `%w` สามารถ wrap error chain ได้, errors.New ไม่สามารถ
- **error message ควร capitalize** — Go convention: error message ไม่ capitalize และไม่มี punctuation ท้าย เช่น `"not found"` ไม่ใช่ `"Not found."`
- **panic ดีกว่า return error สำหรับ critical error** — ใช้ panic เฉพาะสำหรับ programming error ที่ should not happen, ไม่ใช่ expected failure

> 💡 ตัวอย่างจากของจริง
>
> **net/http**: `http.ErrServerClosed` เป็น sentinel error สำหรับ graceful shutdown — caller ตรวจด้วย `errors.Is(err, http.ErrServerClosed)`
>
> **database/sql**: `sql.ErrNoRows` เป็น sentinel ที่ทุก Go database driver ใช้ร่วมกัน
