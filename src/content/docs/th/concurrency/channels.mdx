## Channel คืออะไร?

**Channel** คือท่อส่งข้อมูลแบบ typed ที่ goroutines ใช้สื่อสาร การส่งค่าเข้า channel และรับจาก channel เป็นสองคำสั่งที่ถ่ายโอนทั้งข้อมูลและการ synchronize ในขั้นตอนเดียว

```go
ch := make(chan int)   // unbuffered channel of int
ch <- 42              // send  (blocks until a receiver is ready)
v  := <-ch            // receive (blocks until a sender is ready)
```

Type system บังคับสิ่งที่ไหลผ่าน channel `chan string` ไม่ยอมรับ `int`

## Unbuffered vs Buffered

| | Unbuffered | Buffered |
|--|-----------|---------|
| **สร้างด้วย** | `make(chan T)` | `make(chan T, capacity)` |
| **Send บล็อก?** | ใช่ — จนกว่า receiver พร้อม | ไม่ — จนกว่า buffer เต็ม |
| **Receive บล็อก?** | ใช่ — จนกว่า sender พร้อม | ไม่ — จนกว่า buffer ว่าง |
| **Synchronize?** | ใช่ — sender และ receiver พบกันในเวลาเดียวกัน | ไม่ — buffer แยกเวลาออกจากกัน |

Unbuffered channels ให้ synchronization guarantee ที่แข็งแกร่งที่สุด: sender รู้ว่า receiver ได้รับค่าแล้วก่อนที่จะดำเนินต่อ

## ทิศทางของ Channel

คุณสามารถจำกัด channel parameter ให้เป็น send-only หรือ receive-only เพื่อแสดง intent ใน type:

```go
func producer(out chan<- int) { out <- 1 }   // send-only
func consumer(in <-chan int)  { v := <-in; _ = v }  // receive-only
```

`chan T` ที่เป็นสองทิศทางสามารถ assign ให้กับ direction ไหนก็ได้ Compiler จะบังคับว่า receive-only channel จะถูกส่งเข้าไม่ได้ และในทางกลับกันก็เช่นกัน

## การปิด Channel และ Range

Sender เรียก `close(ch)` เพื่อบอกว่าจะไม่มีค่าอีกแล้ว Receivers ใช้ `for range` loop เพื่อดึงค่าทั้งหมดจนกว่าจะ close:

```go
close(ch)
for v := range ch { // exits when ch is closed and empty
    fmt.Println(v)
}
```

## Comma-ok Receive Idiom

Receive expression สามารถ return boolean ตัวที่สองที่บอกว่า channel ยังเปิดอยู่หรือไม่:

```go
v, ok := <-ch
// ok == true  → v is a real value
// ok == false → channel is closed and drained; v is the zero value
```

## Nil Channel

Channel variable ที่แค่ประกาศ แต่ไม่เคย `make` คือ **nil**:

```go
var ch chan int // nil — not the same as make(chan int)
```

ทุก operation บน nil channel จะ block **ตลอดไป** — ไม่ panic, block คือ send และ receive บน nil channel ทั้งคู่ทำให้ goroutine หยุดรอโดยไม่มีอะไรมาปลุกมันได้เลย:

```go
var ch chan int
<-ch // blocks forever
```

ถ้ารันเป็น goroutine เดียวใน `main` นี่คือ **deadlock** จริง ๆ: สถานะที่ชุด goroutine ทั้งหมด block รออยู่ โดยแต่ละตัวรอสิ่งที่มีแต่ goroutine อื่นที่ block อยู่ในชุดเดียวกันเท่านั้นที่ให้ได้ ทำให้ไม่มีตัวไหนไปต่อได้เลย Go runtime ตรวจจับกรณีเฉพาะที่ *ทุก* goroutine ใน program block พร้อมกัน แล้วจบด้วย `fatal error` ไม่ใช่ panic — `recover()` เรียกไม่ได้:

```text
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan receive (nil chan)]:
main.main()
	/tmp/nilchandeadlock/main.go:5 +0x2c
exit status 2
```

Tag `[chan receive (nil chan)]` ใน goroutine trace คือตัวบอกใบ้ — มันระบุ nil channel เป็นสาเหตุตรง ๆ ไม่ใช่แค่ "block เฉย ๆ" nil channel send ก็ deadlock เหมือนกัน รายงานเป็น `[chan send (nil chan)]` นี่คือเหตุผลที่ struct field แบบ `chan` ที่เป็น zero value ที่ลืม initialize เป็นบัค AI-generated คลาสสิก: มัน compile ผ่าน แล้ว hang ทันทีที่มีอะไรไปแตะมันครั้งแรก

Nil channel ไม่ได้เป็นแค่บัคเสมอไป — case ที่เป็น nil ใน `select` จะถูก *ปิดใช้งาน* แทนที่จะ block ซึ่งเป็นเทคนิคที่ตั้งใจใช้ อธิบายในบท Select

## ตาราง Channel Operation ฉบับสมบูรณ์

สาม operation — send, receive, `close` — ทำงานต่างกันขึ้นอยู่กับว่า channel เป็น nil, open, หรือ closed:

| Operation | nil channel | open channel | closed channel |
|---|---|---|---|
| `ch <- v` (send) | block ตลอดไป | block จนกว่า receiver พร้อม (unbuffered) หรือ buffer มีที่ว่าง | **panic**: `send on closed channel` |
| `<-ch` (receive) | block ตลอดไป | block จนกว่ามีค่า | return ทันที: zero value, `ok == false` |
| `close(ch)` | **panic**: `close of nil channel` | close สำเร็จ — receiver ที่ block อยู่ unblock ทันที | **panic**: `close of closed channel` |
| `len(ch)` | `0` | จำนวน element ใน buffer ที่ยังไม่ถูกรับ | จำนวน element ใน buffer ที่ยังเหลือ |
| `cap(ch)` | `0` | ความจุของ buffer | ความจุของ buffer (ไม่เปลี่ยนหลัง close) |

panic message ทั้งสาม และ deadlock message ด้านบน copy มาจาก output จริงของ `go run` บน Go 1.26.5 คำเดียวที่ต้องจำ: **nil block, closed panic ตอน send และไม่ block เลยตอน receive**

export const channelsCode = `package main

import "fmt"

func producer(ch chan<- int, n int) {
\tfor i := 1; i <= n; i++ {
\t\tch <- i
\t}
\tclose(ch)
}

func main() {
\t// Unbuffered channel: producer runs in a goroutine
\tch := make(chan int)
\tgo producer(ch, 5)
\tfor v := range ch {
\t\tfmt.Println(v)
\t}

\tfor s := range buf {
\t\tfmt.Println(s)
\t}

\tdone := make(chan bool, 1)

## close คือสัญญาณ Broadcast

การ close channel จะปลุก **ทุก** goroutine ที่ block รออยู่บนมัน ไม่ใช่แค่ตัวเดียว — ต่างจาก receive ปกติที่ส่งค่าให้ goroutine ที่รออยู่แค่ตัวเดียวเท่านั้น เมื่อรวมกับ `chan struct{}` นี่คือวิธี idiomatic ในการ broadcast "stop" หรือ "ready" ไปยัง goroutine จำนวนไม่จำกัดพร้อมกัน

`struct{}` คือ empty struct — ไม่มี field เลยและกินพื้นที่ 0 byte `chan struct{}` ถูกใช้เป็นสัญญาณล้วน ๆ ไม่มีใครสนใจค่าที่รับได้ สนใจแค่ว่า receive มัน unblock:

```go
done := make(chan struct{})

go func() {
    <-done // unblocks the instant done is closed
    fmt.Println("goroutine 1 saw the signal")
}()
go func() {
    <-done // unblocks at the same instant, independently
    fmt.Println("goroutine 2 saw the signal")
}()

close(done) // broadcasts to both goroutines simultaneously
```

ถ้าส่งค่าเดียวเข้า `done` จะปลุกแค่หนึ่งใน goroutine ทั้งสอง — อีกตัวจะ block ตลอดไป `close` เป็น channel operation เดียวที่ไปถึงทุก waiter พร้อมกัน

## Happens-before และ Channel Ownership

Channel ไม่ใช่แค่ความสะดวกด้าน scheduling — มันเป็นส่วนหนึ่งของการรับประกันใน [Go memory model](https://go.dev/ref/mem) เรื่องว่าเมื่อไหร่ write ที่ทำใน goroutine หนึ่งจะมองเห็นได้ใน goroutine อีกตัว กฎคือ: **send บน channel เกิด happens-before receive ที่จับคู่กันเสร็จสมบูรณ์** และสำหรับ channel ที่มี capacity `C` การ send ครั้งที่ k จะ happens-before การ receive ครั้งที่ (k+C) เสร็จสมบูรณ์ ในทางปฏิบัติหมายความว่า variable ใด ๆ ที่ goroutine เขียน *ก่อน* มัน send บน channel จะมองเห็นได้แน่นอนโดย goroutine ที่อ่านมัน *หลังจาก* receive จาก channel นั้น — ไม่ต้องใช้ mutex หรือ atomic แยกสำหรับการส่งต่อนี้

การรับประกันนี้ยังเป็นเหตุผลที่ Go channel มี **กฎ ownership** ชัดเจน: goroutine ที่สร้าง channel คือตัวที่ send และ close มัน ส่วน goroutine อื่นทุกตัวถือแค่ `<-chan T` แบบ receive-only เท่านั้น ไม่เคย close หรือ send เลย function ที่ return channel ควร return เป็น directional type เพื่อให้ compiler บังคับได้ ไม่ใช่แค่ตาม convention:

```go
// producer owns out: it is the only goroutine that sends to it or closes it.
func producer(n int) <-chan int {
	out := make(chan int, n)
	go func() {
		defer close(out) // the owner closes, always
		for i := 1; i <= n; i++ {
			out <- i
		}
	}()
	return out // callers only ever see <-chan int
}
```

การละเมิดกฎนี้ — เช่น goroutine สองตัวคิดว่าตัวเองเป็นเจ้าของ channel เดียวกันและเรียก `close` ทั้งคู่ — คือบัคที่อยู่ใน section "อ่านโค้ดที่ AI เขียน" ด้านล่างของบทนี้เป๊ะ

## Buffered Channel เป็น Semaphore

Capacity ของ buffered channel ใช้เพื่อการนับล้วน ๆ ได้ ไม่ต้องส่งข้อมูลจริง — นี่คือ implementation แบบคลาสสิกของ counting semaphore ใน Go acquire permit ด้วยการ send เข้า channel (block เมื่อ buffer เต็ม); release ด้วยการ receive:

```go
sem := make(chan struct{}, 2) // at most 2 permits

sem <- struct{}{} // acquire — blocks if 2 permits are already out
// ... critical section, at most 2 goroutines here at once ...
<-sem // release
```

นี่คือรูปแบบง่ายที่สุดของ bounded-parallelism pattern ที่อธิบายเต็ม ๆ ในบท Patterns — ควรรู้จักไว้ตรงนี้เพราะเป็นการใช้ capacity ของ buffered channel แบบที่สอง ต่างจากแค่ "ช่วยปรับ timing ให้ราบรื่น"

snippet ด้านล่างรันทั้งสามไอเดีย: `close` เป็น broadcast ไปยัง 3 goroutine ที่รออยู่, `chan struct{}` ที่ buffer เป็น 2 ใช้เป็น semaphore, และ producer ที่เป็นเจ้าของ channel ของตัวเองตั้งแต่ต้นจนจบ

export const channelsOwnershipCode = `package main

import (
\t"fmt"
\t"sort"
\t"sync"
)

func main() {
\t// close as broadcast: every receiver unblocks the instant the channel
\t// closes, no matter how many goroutines are waiting.
\tdone := make(chan struct{})
\tvar wg sync.WaitGroup
\tresults := make([]string, 3)
\tfor i := 0; i < 3; i++ {
\t\twg.Add(1)
\t\tgo func(id int) {
\t\t\tdefer wg.Done()
\t\t\t<-done // unblocks for every goroutine at once when done is closed
\t\t\tresults[id] = fmt.Sprintf("worker %d saw the broadcast", id)
\t\t}(i)
\t}
\tclose(done) // broadcasts to all 3 waiters simultaneously
\twg.Wait()
\tfor _, r := range results {
\t\tfmt.Println(r)
\t}

\t// buffered channel as a counting semaphore: only 2 permits, so at most 2
\t// goroutines run their critical section concurrently.
\tsem := make(chan struct{}, 2)
\tvar mu sync.Mutex
\tinFlight, maxInFlight := 0, 0
\tvar wg2 sync.WaitGroup
\tfor i := 0; i < 5; i++ {
\t\twg2.Add(1)
\t\tgo func() {
\t\t\tdefer wg2.Done()
\t\t\tsem <- struct{}{} // acquire
\t\t\tmu.Lock()
\t\t\tinFlight++
\t\t\tif inFlight > maxInFlight {
\t\t\t\tmaxInFlight = inFlight
\t\t\t}
\t\t\tmu.Unlock()

\t\t\tmu.Lock()
\t\t\tinFlight--
\t\t\tmu.Unlock()
\t\t\t<-sem // release
\t\t}()
\t}
\twg2.Wait()
\tfmt.Println("never exceeded 2 concurrent holders:", maxInFlight <= 2)

\t// ownership: the sender both sends and closes; the consumer only ever
\t// holds a <-chan so it physically cannot close or send.
\tch := ownedProducer(3)
\tvar got []int
\tfor v := range ch {
\t\tgot = append(got, v)
\t}
\tsort.Ints(got)
\tfmt.Println(got)
}

// ownedProducer owns out: it is the only goroutine that sends to it or
// closes it. Callers only ever see the receive-only <-chan int.
func ownedProducer(n int) <-chan int {
\tout := make(chan int, n)
\tgo func() {
\t\tdefer close(out)
\t\tfor i := 1; i <= n; i++ {
\t\t\tout <- i
\t\t}
\t}()
\treturn out
}`;

## Mental Model

```text
Unbuffered channel — rendez-vous point:

G1 ──send──→ [channel] ←──recv── G2
             (block)   (block)
             G1 และ G2 ต้องพบกัน

Buffered channel (cap=3):

G1 ──send──→ [_][_][_] ←──recv── G2
             (block เมื่อ full)
             (block เมื่อ empty)
             G1/G2 ทำงานอิสระมากกว่า
```

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| unbuffered channel | synchronization guarantee แข็งแกร่ง | G ส่ง block จนกว่า G รับพร้อม |
| buffered channel | decouple sender/receiver timing | ต้อง size buffer ให้เหมาะ, อาจ hide backpressure |
| channel direction (`chan<-`, `<-chan`) | compile-time safety | verbose ใน function signature |
| close + range | notify completion ง่าย | ส่งหลัง close → panic |

## ความเข้าใจผิดที่พบบ่อย

- **channel เสมอเร็วกว่า mutex** — channel มี overhead มากกว่า mutex สำหรับ simple counter
- **buffered channel ช่วยป้องกัน deadlock** — ไม่เสมอ — deadlock ยังเกิดได้ถ้า buffer เต็มและไม่มี receiver
- **close(ch) ลบข้อมูลใน buffer** — ไม่ — receiver ยังรับข้อมูลที่เหลือใน buffer ได้หลัง close
- **สามารถ close channel จาก receiver ได้** — sender เท่านั้นที่ควร close channel

## อ่านโค้ดที่ AI เขียน

เมื่อโค้ดที่ AI สร้างมาสร้างหรือ close channel ให้เช็กสิ่งเหล่านี้ก่อนเชื่อมัน:

- มี goroutine เดียวเท่านั้นที่เรียก `close` บน channel นี้จริงไหม หรือมีโอกาสที่ goroutine สองตัวจะเรียก `close` บนตัวเดียวกัน?
- ทุก goroutine ที่ send บน channel นี้มี receiver ที่การันตีว่ายังอ่านอยู่จริงไหม หรือ receiver อาจ return ไปแล้ว ทำให้ sender block ตลอดไป?
- มี channel variable ที่ถูกใช้ก่อน `make` หรือเปล่า (field แบบ channel ที่เป็น zero value ของ struct หรือ `var ch chan T` ที่ไม่เคยถูก assign)? ทุก operation บนมันจะ block ตลอดไปแทนที่จะ panic
- function ที่ send อย่างเดียวประกาศ channel parameter เป็นสองทิศทาง (`chan T`) แทนที่จะเป็น `chan<- T` หรือเปล่า? ไม่ใช่บัค แต่พลาดโอกาสให้ compiler ช่วยป้องกัน receive โดยไม่ตั้งใจ
- ทุก path — รวมถึง error return — ทำให้ send-after-close เป็นไปไม่ได้จริงไหม หรือมี branch ที่ early-return ข้ามจุดที่ channel ถูก close ไปแล้ว?

`go run -race` ยังรายงาน `WARNING: DATA RACE` ระหว่าง send ที่แข่งกันกับ receive ที่ trigger close เพิ่มด้วย — นี่คือคำถาม "ใคร close" เรื่อง ownership จากก่อนหน้านี้ในบทนี้เป๊ะ วิธีแก้: ไม่มีใครใน goroutine ต่อ channel เรียก close(out) เลย goroutine เฉพาะทางตัวเดียวเรียก `wg.Wait()` แล้วค่อย `close(out)` แค่ครั้งเดียว หลังจาก input goroutine ทุกตัวเสร็จแล้ว — ดู fan-in `merge` เวอร์ชันที่แก้แล้วในบท Patterns
</SpotTheBug>

<Callout title="ข้อควรระวัง: ส่งเข้า channel ที่ปิดแล้วจะ panic">
การเรียก `close(ch)` แล้วส่งเข้า `ch` จะทำให้เกิด runtime panic การรับจาก channel ที่ปิดแล้วไม่มีทาง panic — แต่จะ return zero value ของ type นั้น และ return value ตัวที่สอง comma-ok จะเป็น `false` หลักง่าย ๆ: เฉพาะ **sender** เท่านั้นที่ปิด channel และปิดก็ต่อเมื่อรู้ว่าจะไม่ส่งอีกแล้ว อย่าปิด channel จากฝั่ง receiver
</Callout>
