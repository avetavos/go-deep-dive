## Goroutine คืออะไร?

**Goroutine** คือฟังก์ชันที่ทำงานพร้อมกันกับ goroutines อื่น ๆ ในพื้นที่ address เดียวกัน คุณสร้างได้ด้วย keyword เดียว:

```go
go f(args)
```

นั่นคือ syntax ทั้งหมด `go` จัดตาราง `f` ให้รัน concurrent แล้ว goroutine ที่เรียกก็ดำเนินต่อทันทีโดยไม่รอให้ `f` return

## ทำไม Goroutines ถึงถูก

OS thread โดยทั่วไปเริ่มต้นด้วย stack ขนาดคงที่ 1–8 MB แต่ goroutine เริ่มต้นด้วย stack ขนาดประมาณ **2–8 KB** ที่ขยายและหดตัวได้อัตโนมัติตามต้องการ Go runtime จัดสรร goroutines ลง OS threads โดยใช้ **M:N scheduler** (M goroutines บน N threads) Context switch ระหว่าง goroutines เกิดขึ้นใน user-space และถูกกว่า kernel thread switch หลายเท่า

ในระบบ production การมี goroutines หลายหมื่นตัวรันพร้อมกันเป็นเรื่องปกติ

## Go Scheduler: M, P, G

Scheduler ทำงานบนสามแนวคิด:

| สัญลักษณ์ | ความหมาย |
|--------|---------|
| **G** | Goroutine — หน่วยงาน concurrent |
| **M** | Machine — OS thread |
| **P** | Processor — scheduling context (มี GOMAXPROCS ตัว) |

แต่ละ P มี run queue ของ Gs M ต้องถือ P ถึงจะรัน G ได้ เมื่อ G บล็อกบน I/O M ที่รันอยู่จะปล่อย P เพื่อให้ M อื่นรับช่วงต่อ

## รอด้วย sync.WaitGroup

`sync.WaitGroup` เป็นวิธีมาตรฐานในการรอ goroutines จำนวนคงที่ให้เสร็จ:

- `wg.Add(n)` — เพิ่ม counter ขึ้น n (เสมอก่อน `go` statement)
- `wg.Done()` — ลด counter ลง 1 (เรียกด้วย `defer` ใน goroutine)
- `wg.Wait()` — บล็อกจนกว่า counter จะถึงศูนย์

### wg.Go — Go 1.25+

ตั้งแต่ Go 1.25 `WaitGroup` มี method `Go` ที่รวม `Add(1)`, `go` statement และ `defer Done()` ไว้ในการเรียกครั้งเดียว:

```go
var wg sync.WaitGroup
for i := 1; i <= 3; i++ {
    wg.Go(func() { work(i) })
}
wg.Wait()
```

`wg.Go` ตัดความผิดพลาดคลาสสิกสองอย่างออกไป — ลืม `Add` ก่อน `go` statement หรือลืม `Done` — และ `go vet` (analyzer `waitgroup`, Go 1.25+) จะเตือนเมื่อวาง `Add` ผิดที่ รูปแบบ `Add/Done` ด้านล่างยังใช้ได้และเป็นสิ่งที่คุณจะเจอในโค้ดเก่า runner ในเบราว์เซอร์เกิดก่อน `wg.Go` playground จึงยังใช้รูปแบบคลาสสิก

export const goroutinesCode = `package main

import (
\t"fmt"
\t"sync"
)

func worker(id int, results []string, wg *sync.WaitGroup) {
\tdefer wg.Done()
\tsum := 0
\tfor j := 1; j <= 5; j++ {
\t\tsum += j
\t}
\tresults[id-1] = fmt.Sprintf("worker %d: sum 1..5 = %d", id, sum)
}

func main() {
\tvar wg sync.WaitGroup
\tresults := make([]string, 3)

\tfor i := 1; i <= 3; i++ {
\t\twg.Add(1)
\t\tgo worker(i, results, &wg)
\t}

\twg.Wait()

\tfor _, r := range results {
\t\tfmt.Println(r)
\t}
\tfmt.Println("all workers done")
}`;

## Runtime ในปี 2026

การเปลี่ยนแปลงของ runtime สามอย่างจาก Go 1.25–1.27 ที่มีผลกับโค้ด goroutine ในชีวิตประจำวัน:

- **`GOMAXPROCS` รู้จัก container (Go 1.25)** — บน Linux ค่า default เคารพ cgroup CPU limit แล้ว pod ที่ถูกจำกัด 2 CPU บน node 64 core จะได้ `GOMAXPROCS=2` แทนที่จะเป็น 64 และ runtime ตรวจซ้ำเป็นระยะหาก limit เปลี่ยน ไม่ต้องใช้ `uber-go/automaxprocs` อีกต่อไป และ `runtime.SetDefaultGOMAXPROCS()` ใช้คืนค่า default หลังตั้งเองด้วยมือ
- **Green Tea garbage collector (default ตั้งแต่ Go 1.26)** — marking phase ที่ออกแบบใหม่ให้ memory locality ดีขึ้น ลด GC overhead ลง 10–40% ในโปรแกรมจริง ไม่ต้องแก้โค้ด ปิดได้ด้วย `GOEXPERIMENT=nogreenteagc`
- **Goroutine leak profile (GA ใน Go 1.27)** — `runtime/pprof` มี profile `goroutineleak` (เสิร์ฟที่ `/debug/pprof/goroutineleak` ผ่าน `net/http/pprof` ด้วย) ที่ใช้ reachability analysis ของ GC หา goroutine ที่ block บน channel หรือ lock ซึ่งไม่มีใครปลดได้อีกแล้ว traceback ของ module `go 1.27+` ยังพิมพ์ goroutine label ของ `runtime/pprof` ทำให้ระบุที่มาของ goroutine ที่รั่วง่ายขึ้น

```go
// ใน server จริง ที่ mount pprof handler ไว้ที่ :6060
import _ "net/http/pprof"

// จากนั้น เมื่อ mount pprof handler ไว้ที่ :6060
// curl "localhost:6060/debug/pprof/goroutineleak?debug=1"
```


## Runtime Behavior

```text
GMP Model:

G  G  G  G  G  G  G  G    ← goroutines (อาจมีหลักแสน)
 ╲ │ ╱    ╲ │ ╱
  [P1]      [P2]           ← P (= GOMAXPROCS, default = #CPU)
   │          │
  [M1]       [M2]          ← M (OS thread)
   │          │
 CPU0        CPU1

เมื่อ G block บน I/O:
  G ──block──→ waiting queue
  M release P → P ถูก M อื่นรับ → G อื่นรัน

Work stealing:
  P1 run queue ว่าง → steal G จาก P2 run queue
```

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| goroutine (2-8 KB stack) | สร้างได้หลักแสนตัว | scheduler overhead ต่อ goroutine |
| dynamic stack growth | ไม่เสีย memory ล่วงหน้า | stack copy cost เมื่อขยาย |
| M:N scheduler | ไม่ block OS thread บน I/O | scheduler complexity, preemption cost |
| work stealing | CPU utilization สูง | cache miss เมื่อ goroutine ย้าย P |

## ความเข้าใจผิดที่พบบ่อย

- **goroutine = OS thread** — goroutine stack เริ่มต้น 2-8 KB, OS thread 1-8 MB
- **สร้าง goroutine ฟรีทั้งหมด** — มี ~4 KB allocation + scheduler bookkeeping ต่อ goroutine
- **GOMAXPROCS มากขึ้น = เร็วขึ้นเสมอ** — I/O-bound workload ได้ประโยชน์น้อยกว่า CPU-bound
- **goroutine leak ไม่เป็นปัญหา** — goroutine ที่ไม่มีทางออกคือ memory leak

> 💡 ตัวอย่างจากของจริง
>
> **Kubernetes** controller manager มี goroutine ต่อ resource type (Pod, Service, Deployment ฯลฯ)
>
> **etcd** ใช้ goroutine ต่อ peer connection สำหรับ raft consensus algorithm
>
> **Prometheus** เปิด goroutine ต่อ scrape job — scrape หลักพัน target พร้อมกัน
