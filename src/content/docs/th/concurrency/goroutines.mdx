## Goroutine คืออะไร?

**Goroutine** คือฟังก์ชันที่ทำงานพร้อมกันกับ goroutines อื่น ๆ ในพื้นที่ address เดียวกัน คุณสร้างมันด้วย keyword เดียว:

```go
go f(args)
```

นั่นคือ syntax ทั้งหมด `go` จัดตาราง `f` ให้รัน concurrent แล้ว goroutine ที่เรียกก็ดำเนินต่อทันทีโดยไม่รอให้ `f` return

## ทำไม Goroutines ถึงถูก

OS thread โดยทั่วไปเริ่มต้นด้วย stack ขนาดคงที่ 1–8 MB แต่ goroutine เริ่มต้นด้วย stack ขนาดประมาณ **2–8 KB** ที่ขยายและหดตัวได้อัตโนมัติตามต้องการ Go runtime จัดสรร goroutines ลง OS threads โดยใช้ **M:N scheduler** (M goroutines บน N threads) Context switch ระหว่าง goroutines เกิดขึ้นใน user-space และถูกกว่า kernel thread switch หลายเท่า

ในระบบ production การมี goroutines หลายหมื่นตัวรันพร้อมกันเป็นเรื่องปกติ

## Go Scheduler: M, P, G

Scheduler ทำงานบนสามแนวคิด:

| สัญลักษณ์ | ความหมาย |
|--------|---------|
| **G** | Goroutine — หน่วยงาน concurrent |
| **M** | Machine — OS thread |
| **P** | Processor — scheduling context (มี GOMAXPROCS ตัว) |

แต่ละ P มี run queue ของ Gs M ต้องถือ P ถึงจะรัน G ได้ เมื่อ G บล็อกบน I/O M ของมันจะปล่อย P เพื่อให้ M อื่นรับช่วงต่อ

## รอด้วย sync.WaitGroup

`sync.WaitGroup` เป็นวิธีมาตรฐานในการรอ goroutines จำนวนคงที่ให้เสร็จ:

- `wg.Add(n)` — เพิ่ม counter ขึ้น n (เสมอก่อน `go` statement)
- `wg.Done()` — ลด counter ลง 1 (เรียกด้วย `defer` ใน goroutine)
- `wg.Wait()` — บล็อกจนกว่า counter จะถึงศูนย์

export const goroutinesCode = `package main

import (
\t"fmt"
\t"sync"
)

func worker(id int, results []string, wg *sync.WaitGroup) {
\tdefer wg.Done()
\tsum := 0
\tfor j := 1; j <= 5; j++ {
\t\tsum += j
\t}
\tresults[id-1] = fmt.Sprintf("worker %d: sum 1..5 = %d", id, sum)
}

func main() {
\tvar wg sync.WaitGroup
\tresults := make([]string, 3)

\tfor i := 1; i <= 3; i++ {
\t\twg.Add(1)
\t\tgo worker(i, results, &wg)
\t}

\twg.Wait()

\tfor _, r := range results {
\t\tfmt.Println(r)
\t}
\tfmt.Println("all workers done")
}`;

## Runtime Behavior

```text
GMP Model:

G  G  G  G  G  G  G  G    ← goroutines (อาจมีหลักแสน)
 ╲ │ ╱    ╲ │ ╱
  [P1]      [P2]           ← P (= GOMAXPROCS, default = #CPU)
   │          │
  [M1]       [M2]          ← M (OS thread)
   │          │
 CPU0        CPU1

เมื่อ G block บน I/O:
  G ──block──→ waiting queue
  M release P → P ถูก M อื่นรับ → G อื่นรัน

Work stealing:
  P1 run queue ว่าง → steal G จาก P2 run queue
```

## Trade-offs

| Feature | Benefit | Cost |
|---------|---------|------|
| goroutine (2-8 KB stack) | สร้างได้หลักแสนตัว | scheduler overhead ต่อ goroutine |
| dynamic stack growth | ไม่เสีย memory ล่วงหน้า | stack copy cost เมื่อขยาย |
| M:N scheduler | ไม่ block OS thread บน I/O | scheduler complexity, preemption cost |
| work stealing | CPU utilization สูง | cache miss เมื่อ goroutine ย้าย P |

## Common Misconceptions

- **goroutine = OS thread** — goroutine stack เริ่มต้น 2-8 KB, OS thread 1-8 MB
- **สร้าง goroutine ฟรีทั้งหมด** — มี ~4 KB allocation + scheduler bookkeeping ต่อ goroutine
- **GOMAXPROCS มากขึ้น = เร็วขึ้นเสมอ** — I/O-bound workload ได้ประโยชน์น้อยกว่า CPU-bound
- **goroutine leak ไม่เป็นปัญหา** — goroutine ที่ไม่มีทางออกคือ memory leak

> 💡 Real World Example
>
> **Kubernetes** controller manager มี goroutine ต่อ resource type (Pod, Service, Deployment ฯลฯ)
>
> **etcd** ใช้ goroutine ต่อ peer connection สำหรับ raft consensus algorithm
>
> **Prometheus** เปิด goroutine ต่อ scrape job — scrape หลักพัน target พร้อมกัน

<Callout title="ข้อควรระวัง: goroutines ที่เริ่มใน main อาจไม่รันถ้า main return ก่อน">
ถ้า `main` return ก่อนที่ goroutine จะมีโอกาสรัน goroutine นั้นจะถูกยกเลิกอย่างเงียบ ๆ Go runtime exit ทันทีที่ `main` goroutine return — มันไม่รอ background goroutines ใช้ `sync.WaitGroup`, channel, หรือ synchronization mechanism อื่น ๆ เพื่อให้ `main` มีชีวิตนานพอให้ goroutines เสร็จสิ้น
</Callout>
