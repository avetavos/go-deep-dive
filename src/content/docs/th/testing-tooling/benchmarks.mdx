## Benchmark คืออะไร?

**benchmark** วัดว่าโค้ดใช้เวลานานเท่าไร Go benchmarks อยู่ในไฟล์ `_test.go` เคียงข้าง unit tests และรันด้วยคำสั่ง `go test` เดียวกัน — เพียงแต่ใช้ flags ต่างกัน

ฟังก์ชัน benchmark มี signature ดังนี้:

```go
func BenchmarkXxx(b *testing.B) {
    // ... setup code (ไม่ถูกวัด) ...
    for b.Loop() {   // Go 1.24+ รูปแบบที่แนะนำ
        // โค้ดที่ต้องการวัด
    }
}
```

ค่า `testing.B` ขับเคลื่อน loop framework จะเริ่มด้วยค่า `b.N` ขนาดเล็กและเพิ่มขึ้นเรื่อยๆ จนกว่า benchmark จะรันนานพอที่จะให้การวัดที่เสถียร คุณไม่ต้องกำหนด `b.N` เอง

## รูปแบบ loop สองแบบ

Go 1.24 แนะนำ `b.Loop()` เป็นทางเลือกที่ดีกว่า classic `b.N` counter loop:

```go
// รูปแบบ classic — ใช้ได้กับ Go ทุกเวอร์ชัน
func BenchmarkFibClassic(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Fibonacci(20)
    }
}

// รูปแบบ modern — Go 1.24+
func BenchmarkFib(b *testing.B) {
    for b.Loop() {
        Fibonacci(20)
    }
}
```

ทั้งสองรูปแบบถูกต้อง `b.Loop()` แนะนำใน Go 1.24+ เพราะจัดการ timer reset ภายในเอง ตั้งแต่ Go 1.26 ไม่ขวางการ inline ของโค้ดที่ benchmark อีกแล้ว จึงไม่เหลือเหตุผลด้าน performance ที่จะใช้ `b.N` และยังเป็นรูปแบบที่แนะนำใน Go 1.27 และมีโอกาสผิดพลาดน้อยกว่า

## Setup ภายนอก loop

หาก benchmark ต้องการ setup ที่ใช้เวลามาก (เปิดไฟล์, สร้าง slice ขนาดใหญ่) ให้ทำก่อน loop รูปแบบ classic `b.N` ต้องเรียก `b.ResetTimer()` เองเพื่อไม่ให้เวลา setup ถูกนับ:

```go
// รูปแบบ classic b.N — ต้องเรียก ResetTimer เอง
func BenchmarkIsPrimeListClassic(b *testing.B) {
    numbers := make([]int, 1000)
    for i := range numbers {
        numbers[i] = i + 2
    }
    b.ResetTimer() // เริ่มวัดจากจุดนี้

    for i := 0; i < b.N; i++ {
        for _, n := range numbers {
            IsPrime(n)
        }
    }
}
```

`b.Loop()` reset timer ให้เองตอนถูกเรียกครั้งแรก (`go doc testing.B.Loop`) รูปแบบ modern ที่เทียบเท่าจึงข้าม `b.ResetTimer()` ไปเลย:

```go
func BenchmarkIsPrimeList(b *testing.B) {
    numbers := make([]int, 1000)
    for i := range numbers {
        numbers[i] = i + 2
    }

    for b.Loop() {
        for _, n := range numbers {
            IsPrime(n)
        }
    }
}
```

`b.Loop` ยังทำให้ผลลัพธ์ของ loop ถูก keep alive อยู่ ทำให้ compiler ไม่สามารถ optimize โค้ดที่ต้องการวัดทิ้งได้ — นี่คือเหตุผลหลักที่ควรเลือกใช้แทน `b.N` ไม่ใช่แค่เรื่อง reset timer อัตโนมัติ

## การรัน benchmarks

Unit tests **ไม่** รัน benchmarks โดยค่าเริ่มต้น ใช้ flag `-bench`:

```bash
# รัน benchmarks ทั้งหมด แสดง memory allocations
go test -bench=. -benchmem ./...

# รันเฉพาะ benchmarks ที่ชื่อตรงกับ pattern
go test -bench=BenchmarkFib -benchmem ./...

# รัน benchmarks อย่างน้อย 5 วินาทีต่อฟังก์ชัน
go test -bench=. -benchtime=5s ./...
```

## การอ่านผลลัพธ์

วัดจริงในเครื่องด้วย `go test -bench=. -benchmem` (Go 1.26.5, Apple M3 Pro) กับ benchmark `Fibonacci(20)` ด้านบน:

```
BenchmarkFibClassic-11    60018    19425 ns/op    0 B/op    0 allocs/op
BenchmarkFib-11           58771    20169 ns/op    0 B/op    0 allocs/op
```

| คอลัมน์ | ความหมาย |
|--------|---------|
| suffix `-11` | ค่า GOMAXPROCS (logical CPUs ของเครื่องที่รัน — เครื่องคุณอาจต่างออกไป) |
| `60018` | จำนวน iterations ที่ benchmark รัน |
| `19425 ns/op` | nanoseconds ต่อ operation (ขึ้นกับ hardware ด้วย — อย่าเทียบข้ามเครื่อง) |
| `0 B/op` | bytes ที่ allocate ต่อ operation (ต้องใช้ `-benchmem`) |
| `0 allocs/op` | heap allocations ต่อ operation (ต้องใช้ `-benchmem`) |

`Fibonacci` ไม่ allocate อะไรเลยเพราะใช้แค่ stack variables — นั่นคือเหตุผลที่ทั้งสองคอลัมน์ alloc เป็นศูนย์ทั้งสองแถว ฟังก์ชันที่สร้าง `[]string` จะแสดงค่าที่ไม่ใช่ศูนย์

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| `go test -bench` | วัด performance ด้วยเครื่องมือ built-in | ต้องรันซ้ำหลายครั้ง ระวัง noise จาก GC และ CPU throttling |
| `b.N` auto-calibration | framework กำหนด iteration count ให้ได้ผลที่เสถียร | ถ้าใส่ setup ใน loop = benchmark นับ setup ด้วย |
| `b.ReportAllocs()` | เห็น heap allocation ต่อ operation ชัดเจน | ต้องเข้าใจ Escape Analysis เพื่อตีความผลลัพธ์ |
| pprof profiling | วิเคราะห์ CPU/memory hotspot เชิงลึก | overhead ขณะ profiling — อย่าใช้ใน production โดยไม่ตั้งใจ |

## ความเข้าใจผิดที่พบบ่อย

- **benchmark result บน dev machine = production** — ต้องคำนึง CPU throttling, GC state, background processes ที่ต่างกัน
- **`b.N` คือจำนวนที่กำหนดเอง** — Go calibrate `b.N` อัตโนมัติให้ benchmark ใช้เวลาประมาณ 1 วินาที — อย่ากำหนดค่า `b.N` เอง
- **`allocs/op = 0` หมายถึง optimal เสมอ** — zero allocation ดี แต่ถ้า CPU work เพิ่มขึ้นแทน อาจไม่ได้ดีกว่า
- **benchmark สำหรับ micro-optimization เท่านั้น** — benchmark ช่วย validate architectural decision ได้ด้วย เช่น channel vs mutex, slice vs map
