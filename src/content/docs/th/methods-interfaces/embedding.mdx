## Composition แทน Inheritance

Go ไม่มี `extends`, ไม่มี base class, และไม่มี virtual dispatch แต่มี **embedding**: คุณวาง type หนึ่งไว้ใน type อื่นโดยไม่มีชื่อ field และ outer type จะได้รับ fields และ methods ทั้งหมดของ inner type ราวกับว่าเป็นของตัวเอง

```go
type Named struct {
    Name string
}

func (n Named) Describe() string { return "Name: " + n.Name }

type Employee struct {
    Named              // embedded — ไม่มีชื่อ field
    Department string
}
```

ตอนนี้ `Employee` มี field `Name` และ method `Describe()` ที่ promote จาก `Named`:

```go
e := Employee{Named: Named{Name: "Alice"}, Department: "Engineering"}
fmt.Println(e.Name)       // promoted field
fmt.Println(e.Describe()) // promoted method
```

## Promotion ทำงานอย่างไร

เมื่อคุณเข้าถึง `e.Name`, Go มองหา field หรือ method ชื่อ `Name` ใน `Employee` โดยตรงก่อน ถ้าไม่พบ compiler จะค้นหาตาม **depth**: field หรือ method ที่อยู่ตื้นกว่าจะชนะ ถ้าสอง candidate อยู่ที่ depth เดียวกัน จะเป็น ambiguous และการใช้ selector นั้นเป็น compile error:

```go
type A struct{ Name string }
type B struct{ Name string }

type E struct {
    A
    B
}

e := E{A{"a"}, B{"b"}}
e.Name // compile error: ambiguous selector e.Name
```

Promotion ถูก resolve ที่ compile time และ promoted methods เข้าร่วม method set ของ outer type — นี่คือเหตุผลที่ `Employee` satisfy `Describer` ด้านล่าง รูปแบบยาว `e.Named.Name` ใช้ได้เสมอ แม้ในกรณีที่รูปแบบสั้นจะ ambiguous

คุณสามารถ **override** promoted method ได้โดยประกาศ method ที่มีชื่อเดียวกันบน outer type:

```go
func (e Employee) Describe() string {
    return fmt.Sprintf("%s in %s", e.Name, e.Department)
}
```

ตอนนี้ `e.Describe()` เรียก method ของ outer แต่ inner method ยังเข้าถึงได้ผ่าน `e.Named.Describe()`

## Interface embedding

Interfaces ยัง embed interfaces อื่นได้:

```go
type Stringer interface {
    String() string
}

type Describer interface {
    Stringer            // embeds Stringer
    Describe() string
}
```

type ใดที่ตอบสนอง `Describer` ก็ตอบสนอง `Stringer` โดยอัตโนมัติ standard library ใช้สิ่งนี้อย่างกว้างขวาง: `io.ReadWriter` embeds `io.Reader` และ `io.Writer`

## Embedding ไม่ใช่ Inheritance

ความแตกต่างสำคัญ:

| Inheritance (Java/C++) | Embedding (Go) |
|------------------------|----------------|
| Virtual dispatch: การเรียก method ผ่าน base type จะ dispatch ไปยัง override ของ derived | ไม่มี virtual dispatch: การเรียก inner method เรียก *method นั้น* เสมอ ไม่ว่า outer type จะมีอะไร |
| `instanceof` / type hierarchy | ไม่มี hierarchy — types ไม่มีความสัมพันธ์ |
| Base class อ้างถึง derived class ได้ผ่าน virtual methods | Embedded type ไม่รู้จัก outer type |

เพราะไม่มี virtual dispatch, embedding ไม่อนุญาต polymorphism บน outer type ในการได้ polymorphism คุณยังต้องการ interface

export const embeddingCode = `package main

import "fmt"

type Named struct {
\tName string
}

func (n Named) String() string {
\treturn "Named(" + n.Name + ")"
}

func (n Named) Describe() string {
\t// Describe calls String on itself — always Named's String, never an outer override
\treturn "Name: " + n.String()
}

type Employee struct {
\tNamed
\tDepartment string
}

// Employee's own String — NOT used by Named.Describe() above
func (e Employee) String() string {
\treturn fmt.Sprintf("%s (Dept: %s)", e.Name, e.Department)
}

// Interface embedding
type Stringer interface {
\tString() string
}

type Describer interface {
\tStringer
\tDescribe() string
}

func print(d Describer) {
\tfmt.Println(d.String())   // Employee's own String, reached through the interface
\tfmt.Println(d.Describe()) // promoted Describe still calls Named's String, not Employee's
}

func main() {
\te := Employee{
\t\tNamed:      Named{Name: "Alice"},
\t\tDepartment: "Engineering",
\t}
\t// promoted field and method
\tfmt.Println(e.Name)       // Alice
\tfmt.Println(e.Describe()) // Name: Named(Alice) — Named's own String, not Employee's override
\tprint(e)
}`;

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| struct embedding | reuse fields และ methods โดยไม่ต้อง inheritance | field shadowing ถ้า outer type มี field ชื่อเดียวกับ embedded type |
| interface embedding | compose interface ขนาดใหญ่จาก interface เล็ก | ยิ่ง interface ใหญ่ implement ยิ่งยาก |
| method promotion | เรียก method ของ embedded type โดยตรง | อาจสับสนว่า method มาจาก type ใดเมื่อมี embedding หลายชั้น |

## ความเข้าใจผิดที่พบบ่อย

- **embedding = inheritance** — embedded type ไม่รู้จัก outer type; ไม่มี virtual dispatch; ไม่มี IS-A relationship
- **embedding สร้าง subtype relationship** — Person ที่ embed Address ไม่ใช่ subtype ของ Address — เป็นแค่ composition
- **promoted method ทำงานบน outer type** — promoted method เรียก receiver ของ embedded type เสมอ ไม่ใช่ outer type

> 💡 ตัวอย่างจากของจริง
>
> **io.ReadWriter** embed io.Reader และ io.Writer — type ที่ implement ทั้งสองอัตโนมัติ satisfy io.ReadWriter โดยไม่ต้องประกาศเพิ่ม
>
> **bufio.ReadWriter** embed `*bufio.Reader` และ `*bufio.Writer` โดยตรง — promote methods `Read`/`Write` (และอื่น ๆ ) ของทั้งสองให้เรียกผ่าน `ReadWriter` ตัวเดียวได้เลย โดยไม่ต้อง duplicate code

<Callout title="Embedding คือ composition ไม่ใช่ inheritance">
ไม่มี virtual dispatch บน outer type `Named.Describe()` เรียก `n.String()` บนตัวเอง ดังนั้นจึง resolve ไปยัง `String` ของ `Named` เองเสมอ — แม้ concrete value จะเป็น `Employee` ที่มี `String()` ของตัวเอง และแม้ `Describe` จะถูกเรียกผ่าน interface `Describer` ก็ตาม เทียบกับ `d.String()` ที่เรียกตรงบน interface: มัน dispatch ไปยัง override ของ `Employee` เพราะ call นั้นไม่ได้ผ่าน `Named` เลย นี่เป็นเจตนา: embedding ของ Go คือกลไก code-reuse ไม่ใช่กลไก polymorphism สำหรับ polymorphism ให้นิยาม interface และให้ทั้งสอง types ตอบสนองอย่างอิสระ
</Callout>
