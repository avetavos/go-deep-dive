## Go's built-in testing story

Most languages require a third-party testing framework. Go ships everything you need inside the standard library. The `testing` package provides `*testing.T` for unit tests, `*testing.B` for benchmarks, and `*testing.F` for fuzzing — all driven by a single command: `go test`.

The `go` toolchain that ships with every Go installation also includes:

| Tool | Purpose |
|------|---------|
| `go test` | Run tests and benchmarks |
| `go build` | Compile packages and binaries |
| `go run` | Compile and run in one step |
| `go fmt` | Format source code (wraps `gofmt`) |
| `go vet` | Static analysis for common mistakes |
| `go mod` | Module and dependency management |
| `go doc` | Browse package documentation |

## What this module covers

1. **go-test** — Writing `_test.go` files, `func TestXxx(t *testing.T)`, table-driven tests with `t.Run`, `t.Parallel`, fuzzing with `*testing.F`, and everything else `*testing.T` gives you.
2. **benchmarks** — Measuring performance with `func BenchmarkXxx(b *testing.B)`, reading `-benchmem` output, and comparing runs with `benchstat`.
3. **modules** — Managing dependencies with `go mod init`, `go.mod`, `go.sum`, `go get`, and how version resolution actually works.
4. **go-tooling** — The everyday commands: `go run`, `go build`, `go fmt`, `go vet`'s bug-catching analyzers, `go doc`, and the wider linting ecosystem.

## A function worth testing

The best way to appreciate Go's testing tools is to start with a pure function — one with no side effects, no I/O, just input and output. The playground below runs `Fibonacci` from `main`. In the next lesson you will write a proper `_test.go` file for exactly this kind of function — including a fuzz test, since `Fibonacci` and `IsPrime` both take a single `int` and are exactly the shape `*testing.F` is good at hammering with edge-case inputs.

export const indexCode = `package main

import "fmt"

// Fibonacci returns the nth Fibonacci number (0-indexed).
// fib(0)=0, fib(1)=1, fib(2)=1, fib(3)=2, ...
func Fibonacci(n int) int {
\tif n <= 1 {
\t\treturn n
\t}
\treturn Fibonacci(n-1) + Fibonacci(n-2)
}

// IsPrime reports whether n is a prime number.
func IsPrime(n int) bool {
\tif n < 2 {
\t\treturn false
\t}
\tfor i := 2; i*i <= n; i++ {
\t\tif n%i == 0 {
\t\t\treturn false
\t\t}
\t}
\treturn true
}

func main() {
\t// Print the first 10 Fibonacci numbers
\tfmt.Println("Fibonacci sequence:")
\tfor i := 0; i < 10; i++ {
\t\tfmt.Printf("  fib(%d) = %d\\n", i, Fibonacci(i))
\t}

\t// Find primes up to 30
\tfmt.Println("Primes up to 30:")

\t\t\tfmt.Printf("  %d\\n", n)

\t}

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Built-in testing package | No install step, one standard API across every Go project | No assertion library — you write `if got != want` yourself |
| Table-driven tests | Test many cases in one function, easy to add a case | A very long table gets hard to read |
| `go test ./...` | Runs every package's tests in the module in one command | Parallel tests can race on shared state if you are not careful |
| Race detector (`-race`) | Catches concurrency bugs automatically | 2-10x slower — run it in CI, not on every local run |

## Common Misconceptions

- **You need a testing framework like Python or Node's** — the Go standard library already has everything you need; there is no need to install testify or gomega.
- **100% coverage means the code is correct** — coverage only measures whether a line ran, not whether the behavior is correct — a test with no assertions can still reach 100% coverage.
- **`go test` is slow** — `go test` caches results; if nothing changed, it returns the cached result instantly.

<Callout title="Why pure functions make the best first tests">
A pure function — one that depends only on its arguments and always returns the same output for the same input — is the ideal starting point for testing. There is no database to mock, no HTTP server to spin up, and no shared state to reset between runs. `Fibonacci` and `IsPrime` both qualify: call them a thousand times with the same input and you get the same result. The next lesson shows how Go's `testing` package makes writing these tests nearly effortless.
</Callout>

## Reading AI-generated code

Before this module goes into depth, start with the single most common generated-test failure mode: a test that runs, prints `PASS`, and checks nothing.

- Does every `Test*` function actually call `t.Error`/`t.Errorf`/`t.Fatal`/`t.Fatalf` somewhere, or does it just call the function under test and let a `nil` error silently mean success?
- If the function returns a value, is that value ever compared against an expected result — or only checked for "did not panic"?
- Does a benchmark or fuzz test's assertion logic actually depend on the input, or would it pass identically no matter what the function under test returned?

<SpotTheBug code={`func TestParseConfig(t *testing.T) {
	cfg := ParseConfig("timeout=30")
	fmt.Println(cfg) // just prints — never compares to anything
}`}>
This test calls `ParseConfig`, prints the result, and ends — there is no `t.Error`, `t.Errorf`, `t.Fatal`, or comparison against an expected value anywhere. `go test` reports `PASS` for this test unconditionally, whether `ParseConfig` returns a correct struct, an empty one, or silently drops the timeout field entirely. This compiles cleanly and "looks like a test" — which is exactly why it is dangerous: a real bug introduced later will not turn this test red, because nothing in it can ever fail. The fix is a real assertion: `want := Config{Timeout: 30 * time.Second}; if cfg != want { t.Errorf("ParseConfig() = %+v, want %+v", cfg, want) }`.
</SpotTheBug>
