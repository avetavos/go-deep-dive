## What is a benchmark?

A **benchmark** measures how long a piece of code takes to run. Go benchmarks live in `_test.go` files alongside unit tests and are run by the same `go test` command — just with different flags.

A benchmark function has this signature:

```go
func BenchmarkXxx(b *testing.B) {
    // ... setup code (not measured) ...
    for b.Loop() {   // Go 1.24+ preferred form
        // code under measurement
    }
}
```

The `testing.B` value drives the loop. The framework starts with a small value for `b.N` and keeps increasing it until the benchmark runs long enough to produce a stable measurement. You never set `b.N` yourself.

## Two loop forms

Go 1.24 introduced `b.Loop()` as the preferred alternative to the classic `b.N` counter loop:

```go
// Classic form — works in all Go versions
func BenchmarkFibClassic(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Fibonacci(20)
    }
}

// Modern form — Go 1.24+
func BenchmarkFib(b *testing.B) {
    for b.Loop() {
        Fibonacci(20)
    }
}
```

Both forms are correct. `b.Loop()` is preferred in Go 1.24+ because it handles timer reset internally and is less error-prone; since Go 1.26 it no longer blocks inlining of the benchmarked call, so there is no performance reason left to keep `b.N`, and it remains the recommended form in Go 1.27.

## Setup outside the loop

If your benchmark needs expensive setup (opening a file, building a large slice), do it before the loop. With the classic `b.N` form you must call `b.ResetTimer()` yourself so setup time is not counted:

```go
// Classic b.N form — needs an explicit ResetTimer
func BenchmarkIsPrimeListClassic(b *testing.B) {
    numbers := make([]int, 1000)
    for i := range numbers {
        numbers[i] = i + 2
    }
    b.ResetTimer() // start measuring from here

    for i := 0; i < b.N; i++ {
        for _, n := range numbers {
            IsPrime(n)
        }
    }
}
```

`b.Loop()` resets the timer itself the first time it is called (`go doc testing.B.Loop`), so the equivalent modern form skips `b.ResetTimer()` entirely:

```go
func BenchmarkIsPrimeList(b *testing.B) {
    numbers := make([]int, 1000)
    for i := range numbers {
        numbers[i] = i + 2
    }

    for b.Loop() {
        for _, n := range numbers {
            IsPrime(n)
        }
    }
}
```

`b.Loop` also keeps the loop's results alive, so the compiler cannot optimise the measured work away — this is the main reason to prefer it over the `b.N` form, not just the automatic timer reset.

## Running benchmarks

Unit tests do **not** run benchmarks by default. Use the `-bench` flag:

```bash
# Run all benchmarks, show memory allocations
go test -bench=. -benchmem ./...

# Run only benchmarks matching a name pattern
go test -bench=BenchmarkFib -benchmem ./...

# Run benchmarks for at least 5 seconds per function
go test -bench=. -benchtime=5s ./...
```

## Reading the output

Measured locally with `go test -bench=. -benchmem` (Go 1.26.5, Apple M3 Pro) against the `Fibonacci(20)` benchmarks above:

```
BenchmarkFibClassic-11    60018    19425 ns/op    0 B/op    0 allocs/op
BenchmarkFib-11           58771    20169 ns/op    0 B/op    0 allocs/op
```

| Column | Meaning |
|--------|---------|
| `-11` suffix | GOMAXPROCS value (logical CPUs on the machine that ran it — yours will differ) |
| `60018` | Number of iterations the benchmark ran |
| `19425 ns/op` | Nanoseconds per operation (also machine-dependent — do not compare across hardware) |
| `0 B/op` | Bytes allocated per operation (needs `-benchmem`) |
| `0 allocs/op` | Heap allocations per operation (needs `-benchmem`) |

`Fibonacci` allocates nothing because it uses only stack variables — that is why both alloc columns are zero on both rows. A function that builds a `[]string` would show non-zero values.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| `go test -bench` | Measures performance with a built-in tool | Needs multiple runs — watch for noise from GC and CPU throttling |
| `b.N` auto-calibration | The framework picks an iteration count that gives a stable result | Setup left inside the loop gets measured too |
| `b.ReportAllocs()` | Shows heap allocations per operation clearly | You need to understand escape analysis to interpret the result |
| pprof profiling | Deep CPU/memory hotspot analysis | Profiling overhead — do not leave it running in production by accident |

## Common Misconceptions

- **A benchmark result on your dev machine matches production** — CPU throttling, GC state, and background processes differ between machines.
- **`b.N` is a count you choose** — Go calibrates `b.N` automatically so the benchmark runs for about a second — never set `b.N` yourself.
- **`allocs/op = 0` always means optimal** — zero allocations is good, but if CPU work went up instead, the result may not actually be better.
- **Benchmarks are only for micro-optimization** — benchmarks can also validate architectural decisions, e.g. channel vs mutex, slice vs map.

<Callout title="Let the framework drive iterations — never set the count yourself">
The benchmark framework controls the iteration count (`b.N` under the hood) to achieve a statistically stable measurement. If you set `b.N` directly or use a fixed loop count, your timings will be unreliable. Also use `-benchmem` as a habit: even functions that look allocation-free sometimes surprise you, and catching unnecessary heap allocations early is far cheaper than profiling in production.
</Callout>
