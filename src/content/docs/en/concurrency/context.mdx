## What is context.Context?

`context.Context` is a standard interface that carries:

- A **cancellation signal** — a goroutine can check `ctx.Done()` to learn that it should stop working
- An optional **deadline or timeout** — work is automatically cancelled when the clock expires
- **Request-scoped key/value pairs** — small amounts of metadata like a request ID or authentication token

The context package solves a concrete problem: when a server request is cancelled (the user closes the browser, the upstream times out), how does every in-flight goroutine spawned for that request know to stop? Passing `context.Context` as the first argument to every I/O function is the Go-standard answer.

## Creating contexts

```go
// Root contexts — never carry cancellation
context.Background()   // top-level root, use in main or test setup
context.TODO()         // placeholder when you are unsure which context to use

// Derived contexts — add cancellation/timeout on top of a parent
ctx, cancel := context.WithCancel(parent)
ctx, cancel := context.WithTimeout(parent, 5*time.Second)
ctx, cancel := context.WithDeadline(parent, time.Now().Add(5*time.Second))
ctx2       := context.WithValue(parent, key, value)
```

Derived contexts form a tree. Cancelling a parent automatically cancels all its children.

## The cancellation contract

When you call `context.WithCancel` or `context.WithTimeout`, you receive two values: the derived context and a `cancel` function. You **must** call `cancel()` when the work is done — even if the context expires naturally. If you don't, the parent context keeps a reference to the child until the parent is also cancelled, which leaks resources.

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel() // always
```

## Listening for cancellation

Inside a goroutine, `ctx.Done()` returns a channel that is closed when the context is cancelled or times out. Use `select` to multiplex it with real work:

```go
select {
case result := <-workCh:
    return result, nil
case <-ctx.Done():
    return "", ctx.Err() // context.Canceled or context.DeadlineExceeded
}
```

## context.WithValue

`context.WithValue` attaches a key/value pair to the context. Use only for request-scoped data that crosses API boundaries (request ID, auth token). Do **not** use it as a general-purpose parameter-passing mechanism — put those in function arguments instead.

To avoid key collisions with other packages, always use a package-private, unexported type as the key:

```go
type contextKey string
const requestIDKey contextKey = "requestID"
```

Prefer a typed getter function over a bare type assertion at every call site — `func requestID(ctx context.Context) (string, bool) { v, ok := ctx.Value(requestIDKey).(string); return v, ok }` — so a missing value is a checked `false` instead of a panic. The comma-ok form matters here for exactly the reason covered in the Reading AI-generated code section below.

## Cause: why was this context cancelled?

`ctx.Err()` only ever returns one of two sentinel values — `context.Canceled` or `context.DeadlineExceeded` — which tells you *that* something happened but never *why*. `context.WithCancelCause` (and `context.WithTimeoutCause` for the deadline case) let you attach a real reason, retrieved later with `context.Cause`:

```go
ctx, cancel := context.WithCancelCause(parent)
cancel(errQuotaExceeded) // the "cause"

ctx.Err()           // context.Canceled -- always the generic sentinel
context.Cause(ctx)  // errQuotaExceeded -- the specific reason
```

`ctx.Err()` stays a stable sentinel that every caller can compare against; `context.Cause(ctx)` is the richer error for logging or a client response. If `cancel` is called with `nil`, the cause is `context.Canceled` — same as plain `WithCancel`.

## WithoutCancel: detaching from a parent's cancellation

Background work that must outlive the request that started it — a cache refresh, an audit log write — should not inherit the parent's cancellation, but usually should still carry its request-scoped values (a trace ID, for logging). `context.WithoutCancel` (Go 1.21) does exactly that: the returned context never reports `Done`, `Err`, or `Cause` from the parent's cancellation, while `Value` lookups still walk up to the parent normally.

```go
func handleRequest(ctx context.Context) {
	go auditLog(context.WithoutCancel(ctx), "request handled")
	// ...respond to the request; ctx may be cancelled the instant this returns
}
```

Reaching for `context.Background()` instead is the common AI-generated mistake here — it detaches from cancellation too, but it also throws away every value the original context carried, including anything a logging or tracing middleware attached upstream.

## AfterFunc: reacting to cancellation without a select

`context.AfterFunc(ctx, f)` (Go 1.21) runs `f` in its own goroutine the moment `ctx` is done — including immediately, in its own goroutine, if `ctx` is already done when you call it. It returns a `stop` function that cancels the association; `stop()` returns `true` only if it prevented `f` from running (if `f` has already started, `stop` returns `false` and does not wait for `f` to finish). This is a lighter-weight alternative to spinning up a small goroutine with a `select` on `ctx.Done()` purely to run a cleanup callback.

## The rules of the road

A short checklist that covers nearly every idiomatic-context violation in generated code:

- `ctx` is always the first parameter, named `ctx`, never bundled into a struct field.
- Never pass a `nil` context — use `context.TODO()` when it is genuinely unclear which context belongs, and replace it once the real one is threaded through.
- An HTTP handler gets its context from the request: `r.Context()`, never a fresh `context.Background()`.
- A `main` that needs to shut down on `SIGINT`/`SIGTERM` uses `signal.NotifyContext(context.Background(), os.Interrupt)` rather than hand-rolling a signal channel.
- Every `WithCancel`/`WithTimeout`/`WithDeadline` gets a `defer cancel()` right next to its creation, covered already in this lesson's callout.

## errors.Is for context errors

`ctx.Err()` returns the exact sentinel values `context.Canceled` and `context.DeadlineExceeded`, so a plain `==` comparison against them works today. Prefer `errors.Is(err, context.Canceled)` anyway once the error has passed through anything that might wrap it — `fmt.Errorf("fetch: %w", ctx.Err())` — because `==` stops working the moment the sentinel is wrapped, while `errors.Is` unwraps the chain to find it:

```go
if errors.Is(err, context.Canceled) {
	// the caller gave up; not worth logging as a failure
} else if errors.Is(err, context.DeadlineExceeded) {
	// ran out of time; may be worth retrying with a longer budget
}
```

## Checking ctx.Err() in a CPU-bound loop

A `select` on `ctx.Done()` only helps when the loop body actually performs a channel operation. A tight, CPU-bound loop with no channel ops anywhere in it — computing over a large slice, say — never reaches a `select` at all, so it will run to completion even after the caller has cancelled it:

```go
for i, item := range hugeSlice {
	if i%1024 == 0 && ctx.Err() != nil { // poll periodically, not every iteration
		return ctx.Err()
	}
	process(item)
}
```

Checking every single iteration is usually wasted overhead for a cheap per-item operation; checking on a stride (every 1024th item, or every N milliseconds via `time.Since`) keeps the overhead negligible while still responding to cancellation promptly.

\tfmt.Println("detached still has value:", bg.Value(ctxKey("reqID")))

\tdone := make(chan struct{})
\tafterCtx, afterCancel := context.WithCancel(context.Background())
\tcontext.AfterFunc(afterCtx, func() {
\t\tfmt.Println("AfterFunc ran because ctx was cancelled")
\t\tclose(done)
\t})
\tafterCancel()
\t<-done
}`;

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| context.WithCancel | propagates cancellation down the tree | must always call cancel(), or the goroutine/context leaks |
| context.WithTimeout | automatic deadline | must handle context.DeadlineExceeded |
| context.WithValue | passes a value through the call stack | not type-safe; use an unexported key to avoid collisions |
| ctx.Done() channel | non-blocking check via select | must be checked in every loop iteration that might run long |

## Common Misconceptions

- **`context.WithValue` is meant for passing business data** — it is for request-scoped metadata only (trace ID, auth token)
- **`cancel()` stops the goroutine immediately** — `cancel()` only sends a signal through a channel; the goroutine must check `ctx.Done()` itself
- **A context can carry a value of any type safely** — `context.Value()` returns `any`; you need a type assertion, and the result can be nil

## Reading AI-generated code

When a generated snippet uses `context.Context`, check for these before trusting it:

- Does every `ctx.Value(key)` call use a comma-ok type assertion (`v, ok := ctx.Value(key).(T)`) instead of a bare one (`ctx.Value(key).(T)`)? A bare assertion panics the instant the key was never set on that context.
- Is `ctx` ever stored in a struct field instead of being passed as the first parameter of every function that needs it?
- Does background work that must survive the request use `context.WithoutCancel(ctx)` — or does it fall back to `context.Background()` and silently lose every value the original context carried?
- Is there a `case <-ctx.Done()` anywhere a CPU-bound loop with no channel operations is supposed to be cancellable? Without an explicit `ctx.Err()` check inside the loop body, cancellation is invisible to it.
- Does error handling compare `err == context.Canceled` directly, when the error might have been wrapped with `%w` somewhere upstream? `errors.Is` is required once wrapping is possible.

func requestID(ctx context.Context) string {
\treturn ctx.Value(ctxKey("reqID")).(string) // bare assertion
}

func main() {
\tctx := context.Background() // reqID was never attached to this context
\tfmt.Println(requestID(ctx))

`ctx.Value(ctxKey("reqID"))` returns `nil` (as an `any`) because nothing ever called `context.WithValue` with that key on this context or any of its ancestors. Asserting a `nil` `any` directly to `string` — a concrete, non-interface type — panics rather than returning the zero value:

```text
panic: interface conversion: interface {} is nil, not string

goroutine 1 [running]:
main.requestID(...)
	/tmp/ctxassert/main.go:11
main.main()
	/tmp/ctxassert/main.go:16 +0x34
```

The fix is the comma-ok form: `v, ok := ctx.Value(ctxKey("reqID")).(string); if !ok { return "" }` (or return an error, depending on whether a missing request ID is expected). This is exactly the typed-getter pattern recommended earlier in this lesson's `context.WithValue` section.
</SpotTheBug>

<Callout title="Always defer cancel() to avoid context leaks">
Every call to `context.WithCancel`, `context.WithTimeout`, or `context.WithDeadline` must be paired with a call to the returned `cancel` function. Forgetting it keeps the child registered in its parent until the parent itself ends — a memory leak, and `go vet`'s `lostcancel` analyzer flags the most obvious cases at compile time. Call `cancel()` even when the timeout will fire on its own: it releases the underlying timer immediately instead of waiting for it to expire. The idiomatic pattern is always: `ctx, cancel := context.WithTimeout(parent, d); defer cancel()`.
</Callout>
