## Three foundational patterns

Go's goroutines and channels compose naturally into a small set of well-understood patterns. Once you recognise them, you can combine them to build arbitrarily complex concurrent systems.

## Pipeline

A **pipeline** is a series of stages connected by channels. Each stage receives values from an upstream channel, transforms them, and sends results to a downstream channel. Stages run concurrently — while stage 2 is processing item N, stage 1 is already working on item N+1.

```
generate → square → print
```

Pipelines are ideal for stream processing where each transformation is independent and the stages can be composed like Unix pipes.

## Fan-out / fan-in

**Fan-out** starts multiple goroutines that read from the same input channel, parallelising work. **Fan-in** merges multiple output channels into one for the consumer to read. Together they implement a parallel processing stage inside a pipeline.

### merge: a real fan-in implementation

`merge` below is the canonical fan-in: it takes any number of input channels and returns one channel carrying every value from all of them.

```go
func merge(cs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	wg.Add(len(cs))
	for _, c := range cs {
		go func(c <-chan int) {
			defer wg.Done()
			for v := range c {
				out <- v
			}
		}(c)
	}
	// A single dedicated goroutine waits for every input goroutine to finish,
	// then closes out exactly once.
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}
```

Two details make this correct where a naive version breaks: `wg.Add(len(cs))` happens once, before any goroutine starts, so `wg.Wait()` can never observe a counter of zero prematurely; and only the dedicated closer goroutine ever calls `close(out)`, exactly once, after confirming every input goroutine has returned. The Channels lesson's Reading AI-generated code section shows the classic broken variant — every input goroutine calling `close(out)` itself — and the real `panic: send on closed channel` and `WARNING: DATA RACE` output that produces.

## Worker pool

A **worker pool** is a fixed set of goroutines that all consume from a shared jobs channel. The pool size caps resource usage (goroutines, connections, file handles) while still processing work concurrently. It is the Go equivalent of a thread pool.

```
main → jobs channel → [worker 1, worker 2, worker 3] → results
```

The runnable example below combines all three patterns: a pipeline with a generator and a squaring stage, followed by a worker pool that processes a batch of jobs deterministically.

export const patternsCode = `package main

import (
\t"fmt"
\t"sort"
\t"sync"
)

// --- Pipeline ---

func generate(nums ...int) <-chan int {
\tout := make(chan int, len(nums))
\tfor _, n := range nums {
\t\tout <- n
\t}
\tclose(out)
\treturn out
}

func square(in <-chan int) <-chan int {
\tout := make(chan int, cap(in))
\tgo func() {
\t\tfor n := range in {
\t\t\tout <- n * n
\t\t}
\t\tclose(out)
\t}()
\treturn out
}

// --- Worker pool ---

func worker(jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
\tdefer wg.Done() // one Done per worker, not per job
\tfor j := range jobs {
\t\tresults <- j * 2
\t}
}

func main() {
\t// Pipeline: 1,2,3,4,5 -> squares
\tnums := generate(1, 2, 3, 4, 5)
\tsquares := square(nums)
\tfor v := range squares {
\t\tfmt.Println(v)
\t}

\t// Worker pool: 3 workers, 5 jobs, each job doubles its value.
\t// wg counts *workers*: Add(numWorkers) once, one Done() per worker
\t// when its "for j := range jobs" loop exits (jobs is closed).
\tconst numJobs = 5
\tconst numWorkers = 3
\tjobs := make(chan int, numJobs)
\tresults := make(chan int, numJobs)
\tvar wg sync.WaitGroup

\twg.Add(numWorkers)
\tfor w := 0; w < numWorkers; w++ {
\t\tgo worker(jobs, results, &wg)
\t}
\tfor j := 1; j <= numJobs; j++ {
\t\tjobs <- j
\t}
\tclose(jobs)

\t// A dedicated goroutine closes results once every worker has
\t// returned — closing from main directly would race with the
\t// workers that are still sending.
\tgo func() {
\t\twg.Wait()
\t\tclose(results)
\t}()

\t// Workers finish in a nondeterministic order, so sort before
\t// printing to get a stable, comparable output.
\tvar out []int
\tfor r := range results {
\t\tout = append(out, r)
\t}
\tsort.Ints(out)
\tfor _, r := range out {
\t\tfmt.Println(r)
\t}
}`;

<Playground code={patternsCode} />

The `wg` here counts *workers*, not jobs: `Add(numWorkers)` runs once before the workers start, and each worker calls `Done()` exactly once — when its `for j := range jobs` loop exits because `jobs` was closed. That is what makes a separate `go func() { wg.Wait(); close(results) }()` necessary: something has to wait for every worker to finish and then close `results`, and it cannot be `main` itself, because `main` is busy draining `results` with `for r := range results` at the same time. On Go 1.25+ each worker's `wg.Add`/`go`/`defer wg.Done()` triple could instead be written as `wg.Go(func() { ... })`; the playground keeps the classic `Add`/`Done` form because its in-browser runner predates that method. Because three workers race to write into `results`, the values arrive in whatever order the scheduler happens to finish them — the code sorts before printing so the output is deterministic despite that.

## A cancellable pipeline

The plain `generate` → `square` pipeline above has no way to stop early — if the consumer walks away, both stages keep running (and leak, per the Goroutines lesson) forever. Giving every stage a `context.Context` and a `select` on `ctx.Done()` fixes that: each stage stops producing the moment the context is cancelled, instead of only when its input closes.

```go
func generate(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return // stop producing once the consumer gives up
			}
		}
	}()
	return out
}

func square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}
```

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

squares := square(ctx, generate(ctx, 1, 2, 3, 4, 5))

var got []int
for v := range squares {
	got = append(got, v)
	if len(got) == 2 {
		cancel() // stop the pipeline after exactly 2 values, deterministically
		break
	}
}
fmt.Println(got) // [1 4] -- always exactly these two, cancel fires at a fixed point
```

Every stage's own `select` is what makes cancellation propagate upstream: `square` stops receiving from `generate`'s output the moment `ctx` is done, which in turn means `generate`'s blocked `out <- n` send also unblocks via its own `ctx.Done()` case instead of blocking forever on a channel nobody is reading anymore.

## Bounded parallelism

A buffered channel used purely as a counting semaphore — introduced in the Channels lesson — caps how many goroutines run their critical section at once, independent of how many goroutines were launched in total:

```go
const n = 6
const limit = 2 // at most 2 tasks run at once

sem := make(chan struct{}, limit)
results := make([]int, n) // pre-sized: every goroutine owns a distinct index
var wg sync.WaitGroup

for i := 0; i < n; i++ {
	wg.Add(1)
	go func(i int) {
		defer wg.Done()
		sem <- struct{}{}        // acquire a permit
		defer func() { <-sem }() // release it on the way out

		results[i] = i * i // each goroutine writes a different index -- no overlap, no race
	}(i)
}
wg.Wait()
fmt.Println(results) // [0 1 4 9 16 25], always in this order despite concurrent writes
```

### Why the indexed writes are not a race

All 6 goroutines write into the *same* `results` slice concurrently, with no mutex around `results[i] = i * i` — and this is correctly race-free, not accidentally so. A data race requires two goroutines to access the *same memory location* with at least one write and no synchronization. Here, `results` is allocated once with `make([]int, n)` before any goroutine starts, so its backing array and length never change, and every goroutine writes to a different index — `results[i]` for a distinct `i` each time. Different indices are different memory locations; there is no overlapping access for the race detector to find. This is exactly the same reasoning behind the worker pool's `results[id-1] = ...` pattern used elsewhere in this course, and it is why `go run -race` reports nothing for this snippet.

The `errgroup.SetLimit` method from the Sync Primitives lesson expresses the same bound declaratively — `g.SetLimit(limit)` instead of a hand-sized channel — and is usually the better choice in real code; the raw semaphore channel is worth knowing because it is what `SetLimit` does internally, and because it needs no external module.

## Graceful shutdown

A production HTTP server needs to stop accepting new connections and finish in-flight requests before the process exits — not drop connections mid-response the instant a deploy sends `SIGTERM`. `signal.NotifyContext` turns an OS signal into a `context.Context`, and `http.Server.Shutdown` does the actual graceful stop:

```go
func main() {
	srv := &http.Server{Handler: mux}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	go func() {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	}()

	<-ctx.Done() // blocks until SIGINT/SIGTERM, then stop() lets the next signal kill it
	stop()

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Println("forced shutdown:", err)
	}
}
```

`srv.Shutdown` stops the listener immediately, then waits (up to the context's deadline) for every in-flight handler to return on its own before returning itself; `ListenAndServe` unblocks with exactly `http.ErrServerClosed`, which is the expected, non-error outcome of a deliberate shutdown, not a failure to log. A separate deterministic version of this — listening on an OS-assigned port and shutting down via a plain `cancel()` instead of waiting for a real OS signal — verified locally with `go run -race`:

```text
server shut down cleanly
Serve returned: true
```

(`true` here is `errors.Is(err, http.ErrServerClosed)`, confirming `Serve` returned because of the shutdown, not a real error.) This variant needs a real TCP listener, so it does not run in this page's browser-based Playground.

The three patterns that don't need a real network connection — fan-in, the cancellable pipeline, and bounded parallelism — are combined in the runnable snippet below.

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| worker pool | caps goroutine count, reuses workers | must tune pool size, more complex than goroutine-per-task |
| fan-out / fan-in | parallel processing, aggregated results | must handle error collection and cancellation |
| pipeline | modular stages, easy backpressure | adds per-item latency (buffering overhead) |
| semaphore (buffered channel) | simple rate limiting | must drain the channel on cancellation |

## Common Misconceptions

- **A worker pool is always faster than goroutine-per-request** — it depends on the workload; an I/O-bound one can be faster with goroutine-per-request
- **A pipeline must have a fixed number of stages** — Go pipelines are flexible; stages can be added or removed dynamically
- **Unlimited fan-out is best** — no limit means resource exhaustion under high load

> 💡 Real-world example
>
> **k8s.io/client-go** uses this same worker-queue pattern as the core of its controller framework, in `util/workqueue/queue.go` — multiple workers pull from the same queue to bound concurrent reconciliation.

## Reading AI-generated code

When a generated snippet combines these patterns, check for these before trusting it:

- In a fan-in `merge`, does every input goroutine call `close(out)` itself, or does exactly one dedicated goroutine call it once, after a `wg.Wait()`?
- Does every stage of a pipeline that should be cancellable actually `select` on `ctx.Done()` around its channel send — or does it only check `ctx.Err()` once at the top, missing a cancellation that arrives mid-loop?
- Is the number of concurrently running goroutines actually bounded by a semaphore, worker pool, or `errgroup.SetLimit` — or does "bounded parallelism" in a comment not match unbounded `go` statements in the code?
- Does a graceful-shutdown handler call `srv.Shutdown(ctx)` with a real timeout, or does it call `os.Exit` immediately on receiving the signal, dropping in-flight requests?
- If multiple goroutines write into a shared slice by index, are the indices actually guaranteed disjoint (no two goroutines can ever compute the same index), or could two of them collide and turn a "safe" indexed write into a real race?

This is the same shared-channel-close bug as the Channels lesson's fan-in `merge`, wearing a worker-pool costume: `out` is shared by all 3 workers, but each one calls `close(out)` when its own `for j := range jobs` loop ends. The first worker to finish closes `out`; the next worker that also finishes calls `close(out)` again and panics — captured real output on Go 1.26.5 (`out` here is buffered, so a worker usually finishes its sends before racing on the close, but the exact failure varies by run):

```text
panic: close of closed channel

goroutine 5 [running]:
main.worker(0xc000020120, 0xc0000201b0, 0xc000012180)
	/tmp/workerclosebug/main.go:13 +0xb0
created by main.main in goroutine 1
	/tmp/workerclosebug/main.go:22 +0x80
```

`go run -race` on a separate run of the identical program instead caught a `WARNING: DATA RACE` between one worker's send and another's close — same root cause, different symptom depending on scheduling. The fix is the same one used throughout this lesson: nobody inside the worker closes `out` — a single `go func() { wg.Wait(); close(out) }()` after launching the workers does it exactly once, as the runnable worker-pool example above does.

<Callout title="Gotcha: goroutine leaks when nobody drains a channel">
If a goroutine is blocked sending to a channel and the receiver exits without draining it, the goroutine is **leaked** — it lives forever in the runtime, wasting memory and a goroutine slot. The fix is always to ensure either: (a) the channel is buffered large enough to accept all sends, (b) a receiver always drains the channel to `close`, or (c) the sender also selects on `ctx.Done()` so it can exit when the work is abandoned. In production, run `go tool pprof` on the goroutine profile to detect leaks.
</Callout>
