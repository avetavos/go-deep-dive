## When channels are not enough

Channels excel at transferring ownership of data between goroutines. But sometimes you simply need to protect a shared value that many goroutines read and write — a cache, a counter, a connection pool. For these cases the `sync` package provides lower-level primitives.

## sync.Mutex

A `sync.Mutex` is a mutual exclusion lock. Only one goroutine can hold the lock at a time; all others block on `Lock()` until the holder calls `Unlock()`.

```go
var mu sync.Mutex
var count int

mu.Lock()
count++
mu.Unlock()
```

Always use `defer mu.Unlock()` immediately after `mu.Lock()` so the lock is released even if the function panics or returns early.

## sync.RWMutex

`sync.RWMutex` is an optimized variant for the read-heavy case. Multiple goroutines can hold a **read lock** simultaneously with `RLock/RUnlock`. A **write lock** (`Lock/Unlock`) is exclusive — it waits for all readers to finish, then blocks new readers until the writer is done.

Use it when reads are far more frequent than writes (e.g., an in-memory cache).

## sync.Once

`sync.Once` executes a function exactly once, regardless of how many goroutines call `Do` concurrently. The canonical use case is lazy, thread-safe initialization:

```go
var once sync.Once
var instance *Config

func getConfig() *Config {
    once.Do(func() {
        instance = loadConfig()
    })
    return instance
}
```

## sync/atomic

The `sync/atomic` package provides lock-free operations on integer and pointer types using CPU hardware instructions. For simple counters or flags, atomics are faster than a mutex because there is no lock contention or context switching.

Since Go 1.19, prefer the typed API: a `var hits atomic.Int64` gives you `hits.Add(1)`, `hits.Load()`, `hits.Store(n)`, and `hits.CompareAndSwap(old, new)` as methods, with no address-of operator to get wrong. The same family covers `atomic.Bool` and `atomic.Pointer[T]` for flags and lock-free pointer swaps. The older function form, `atomic.AddInt64(&counter, 1)`, still works and is what you will read in existing code, but it requires the `int64`/`uint64` it operates on to be 8-byte aligned — a real trap on 32-bit platforms where a struct field can end up misaligned. The typed API sidesteps that alignment requirement entirely, which is the main reason to reach for it in new code.

## sync.WaitGroup.Go (Go 1.25+)

`WaitGroup` is the primitive you reach for most often, and since Go 1.25 it has a shortcut: `wg.Go(f)` does `Add(1)`, starts `f` in a new goroutine, and calls `Done()` when `f` returns.

```go
var wg sync.WaitGroup
for _, url := range urls {
    wg.Go(func() { fetch(url) })   // per-iteration url since Go 1.22, no capture dance
}
wg.Wait()
```

Reach for `wg.Go` in new code — it cannot get the `Add` placement wrong — and let `go fix` rewrite the old triple in existing code: the modernizer that does this was named `waitgroup` in Go 1.26 and renamed `waitgroupgo` in Go 1.27 (to avoid clashing with `go vet`'s own `waitgroup` analyzer, which checks for WaitGroup misuse rather than rewriting code).

## Channels vs mutexes — a practical guide

| Use channels when... | Use mutexes when... |
|----------------------|---------------------|
| Transferring ownership of data | Protecting a shared cache or struct |
| Coordinating goroutine lifecycles | Managing a simple counter or flag |
| Pipelines and fan-out patterns | Read-heavy data with sync.RWMutex |

export const syncCode = `package main

import (
\t"fmt"
\t"sync"
\t"sync/atomic"
)

type SafeCounter struct {
\tmu sync.Mutex
\tv  int
}

func (c *SafeCounter) Inc() {
\tc.mu.Lock()
\tdefer c.mu.Unlock()
\tc.v++
}

func (c *SafeCounter) Value() int {
\tc.mu.Lock()
\tdefer c.mu.Unlock()
\treturn c.v
}

func main() {
\t// sync.Mutex: 100 goroutines each increment once -> 100
\tvar wg sync.WaitGroup
\tc := &SafeCounter{}
\tfor i := 0; i < 100; i++ {
\t\twg.Add(1)
\t\tgo func() {
\t\t\tdefer wg.Done()
\t\t\tc.Inc()
\t\t}()
\t}
\twg.Wait()
\tfmt.Println("counter:", c.Value()) // 100

\t// sync.Once: function runs exactly once despite 3 calls
\tvar once sync.Once
\tfor i := 0; i < 3; i++ {
\t\tonce.Do(func() {
\t\t\tfmt.Println("only once")
\t\t})
\t}

\t// sync/atomic: typed API, 50 goroutines each add 1 -> 50
\tvar hits atomic.Int64
\tfor i := 0; i < 50; i++ {
\t\twg.Add(1)
\t\tgo func() {
\t\t\tdefer wg.Done()
\t\t\thits.Add(1)
\t\t}()
\t}
\twg.Wait()
\tfmt.Println("atomic count:", hits.Load()) // 50
}`;

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| sync.Mutex | simple, fast for simple shared state | the goroutine that locks must always unlock |
| sync.RWMutex | readers run in parallel | RLock overhead exceeds Mutex when writes are frequent |
| sync.Once | thread-safe one-time init | cannot be reset |
| sync/atomic | fastest for a simple counter | limited to primitive types |
| channel | composable, safer | more overhead than a mutex |

## Common Misconceptions

- **A mutex is always slower than a channel** — a mutex is faster than a channel for protecting a simple counter
- **`sync.Map` always replaces `map` + mutex** — `sync.Map` fits read-heavy, append-only access patterns, not a general-purpose map
- **The typed `atomic.Int64` and the old `atomic.AddInt64` are identical** — the old function form requires the variable it operates on to be 8-byte aligned yourself (a real trap on 32-bit platforms); the typed API (`atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`) handles alignment automatically, which is why new code should always prefer it
- **`defer mu.Unlock()` is slower than an explicit unlock** — `defer` has negligible overhead; use it for safety every time

> 💡 Real-world example
>
> **Prometheus client_golang** increments its counter metric lock-free with `atomic.AddUint64` in `prometheus/counter.go` — a hot path called on every metric update, so it avoids lock contention with an atomic instead of a mutex.

<Callout title="Data races: find them with go run -race">
A data race occurs when two goroutines access the same variable concurrently and at least one access is a write, with no synchronization between them. The result is undefined behaviour. Go ships a built-in race detector: run `go run -race main.go` or `go test -race ./...` to instrument your binary. The detector adds roughly 2–20x runtime overhead and is not suitable for production, but it is mandatory in CI. Mutexes, channels, and atomics all eliminate races.
</Callout>
