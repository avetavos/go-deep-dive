## The Go concurrency model

Most languages bolt concurrency on top of shared-memory threads. Go was designed from the ground up around a different idea: **Communicating Sequential Processes (CSP)**, formalized by Tony Hoare in 1978. The Go proverb that captures it best is:

> *Do not communicate by sharing memory; instead, share memory by communicating.*

In practice this means:

- **Goroutines** are independently executing functions. They are cheap — a few kilobytes of stack that grows on demand — so you can have hundreds of thousands running concurrently.
- **Channels** are typed conduits. Goroutines send values into a channel and receive values from another, transferring both data and synchronization in one operation.
- **The scheduler** multiplexes goroutines onto a pool of OS threads (GOMAXPROCS threads by default, one per CPU core). You never manage threads directly.

This design makes concurrent programs easier to reason about. When data flows through channels, ownership is clear: the sender had it, now the receiver has it. No mutex needed for that transfer.

## Your first concurrent Go program

The snippet below launches three goroutines in parallel. Each goroutine writes its result into a pre-allocated slice indexed by its own id, so output is always in order. `sync.WaitGroup` blocks `main` until all three are finished — the Goroutines lesson covers `WaitGroup` itself in depth (including the classic `wg.Add` placement bug); this page only needs it to keep `main` alive long enough to see the output.

export const indexCode = `package main

import (
\t"fmt"
\t"sync"
)

func main() {
\tvar wg sync.WaitGroup
\tresults := make([]string, 3)

\tfor i := 0; i < 3; i++ {
\t\twg.Add(1)
\t\tgo func(id int) {
\t\t\tdefer wg.Done()
\t\t\tresults[id] = fmt.Sprintf("goroutine %d says hello", id)
\t\t}(i)
\t}

\twg.Wait()
\tfor _, r := range results {
\t\tfmt.Println(r)
\t}
\tfmt.Println("main exits")
}`;

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| goroutine vs OS thread | 2-8 KB stack vs 1-8 MB | scheduler overhead |
| CSP (channels) vs shared memory | data flow is explicit | channel overhead is higher than a mutex |
| M:N scheduling | few OS threads needed | scheduler complexity |

## Common Misconceptions

- **A goroutine is an OS thread** — a goroutine is far lighter than a thread; you can create hundreds of thousands of them
- **Concurrent means parallel** — concurrent means juggling multiple tasks; parallel means actually running at the same time on multiple cores
- **Channels are always better than mutexes** — a mutex fits simple shared state; a channel fits data flow

## Reading AI-generated code

Every lesson in this module ends with its own detailed version of this section; here is the survey-level version worth checking on sight, before diving into a generated snippet's details:

- Does `main` (or the calling goroutine) wait for every goroutine it starts — with a `WaitGroup`, a channel, or by returning a channel the caller drains — or can it return while goroutines are still running?
- Does every goroutine have a way to stop, and does anything protect state that more than one goroutine touches?
- If the snippet is presented as deterministic, is the printed order actually forced (sorted, or read back through an indexed slice), or could two runs legitimately print in a different order?

<SpotTheBug code={`func main() {
\tfor i := 0; i < 3; i++ {
\t\tgo func(id int) {
\t\t\tfmt.Println("goroutine", id, "says hello")
\t\t}(i)
\t}
\tfmt.Println("main exits")
}`}>
Nothing here waits for the three goroutines to run before `main` returns. The Go runtime does not keep a process alive for background goroutines — the instant `main` returns, the process exits, whether or not any goroutine has been scheduled yet. Real captured output from two separate runs of this exact program:

```text
main exits
```

```text
main exits
goroutine 0 says hello
```

Both are legitimate outcomes of the same binary — sometimes zero goroutines get a chance to run, sometimes one or two do, entirely depending on scheduling. The fix is the `sync.WaitGroup` this page's own runnable example uses: `main` must not return until it has confirmed every goroutine it started has finished.
</SpotTheBug>

<Callout title="Key point: loop variables are per-iteration since Go 1.22">
Since Go 1.22 (for modules with `go 1.22` or newer) every iteration of a `for` loop gets its own `i`, so `go func() { use(i) }()` captures the value you expect. Before 1.22 the variable was shared and every goroutine could see the final value — that is why older code passes it explicitly, `go func(id int) { ... }(i)`, or copies it with `i := i` (a copy `go fix` now removes). Passing the value as an argument is still fine and makes the dependency visible; just know the bug it once guarded against is gone on Go 1.27.
</Callout>
