## Go's approach to polymorphism

Most object-oriented languages bolt polymorphism onto a class hierarchy: you declare that a type *implements* an interface, you *extends* a base class, and the compiler enforces the lineage. Go throws away the hierarchy entirely.

In Go, **any named type can have methods** (except pointer types and interface types), and **any type that has the right methods automatically satisfies an interface** — no declaration required. This is called *implicit interface satisfaction*, and it is the single most important design decision in the language.

The combination of methods and interfaces gives you:

- **Polymorphism** without inheritance trees.
- **Dependency inversion** without frameworks — accept an interface, return a struct.
- **Composition** without `extends` — embed types to promote their fields and methods.

## A first runnable example

The snippet below defines a method on a struct, declares a one-method interface, and calls the method through the interface — all in under 20 lines.

export const indexCode = `package main

import "fmt"

type Rectangle struct {
\tWidth, Height float64
}

func (r Rectangle) Area() float64 {
\treturn r.Width * r.Height
}

type Sizer interface {
\tArea() float64
}

func printArea(s Sizer) {
\tfmt.Printf("area = %.2f\\n", s.Area())
}

func main() {
\tr := Rectangle{Width: 4, Height: 3}
\tfmt.Println(r.Area())
\tprintArea(r)
}`;

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Implicit interface satisfaction | Decoupled code, no import dependency on the interface | Harder to discover which types implement which interface |
| Value receiver | Cheap to reason about, callable on non-addressable values | Copies the struct on every call |
| Pointer receiver | Can mutate, no copy | Needs a nil-check, needs an addressable value |
| Embedding (composition) | Reuses methods/fields without inheriting | No virtual dispatch — polymorphism still needs an interface |

## Common Misconceptions

- **An interface is like an abstract class.** In Go an interface has only method signatures — no implementation, no state.
- **Embedding is inheritance.** The embedded type has no knowledge of the outer type; there is no override and no virtual dispatch.
- **A nil interface is always `== nil`.** An interface holding a nil pointer is not itself nil — `(nil, nil)` is not the same as `(*T, nil)`. See [Interfaces](./interfaces).

> 💡 Real-world example
>
> The standard library builds on `io.Reader` and `io.Writer` as its core interfaces — `os.File`, `bytes.Buffer`, `net.Conn`, and an HTTP request body all implement the same two methods, so they compose across the whole ecosystem without knowing about each other.
>
> Kubernetes' `runtime.Object` interface (`k8s.io/apimachinery/pkg/runtime`) is satisfied by every Kubernetes API resource — a controller written once against `runtime.Object` works with `Pod`, `Deployment`, and `Service` alike.

<Callout title="The key insight">
`Rectangle` never says `implements Sizer`. It just has a method with the right name and signature. That is all Go needs. If the method set matches, the interface is satisfied — automatically, at compile time.
</Callout>
