## What is a method?

A **method** is a function with a *receiver* — an extra parameter that appears between the `func` keyword and the function name. The receiver binds the function to a named type.

```go
func (r Rectangle) Area() float64 {
    return r.Width * r.Height
}
```

Here `r Rectangle` is the receiver. `Area` is now a method of `Rectangle`, callable as `rect.Area()`.

## Value receivers vs pointer receivers

The receiver can be either a value or a pointer:

```go
func (c Counter) Value() int  { return c.count }   // value receiver
func (c *Counter) Inc()       { c.count++ }        // pointer receiver
```

| | Value receiver `(t T)` | Pointer receiver `(t *T)` |
|--|------------------------|---------------------------|
| **Sees** | A copy of the value | The original value |
| **Can mutate?** | No — mutates the copy only | Yes |
| **Callable on** | Both `T` and `*T` | Both `T` (addressable) and `*T` |
| **Use when** | Read-only; small, cheap to copy | Mutation; large struct; consistent method set |

**Be consistent:** if any method on a type needs a pointer receiver, give *all* methods of that type pointer receivers. Mixing causes subtle method-set issues when the type is used as an interface value.

## Methods on any named type

Methods are not limited to structs. You can define methods on any named type in your package — except pointer types and interface types:

```go
type Celsius float64

func (t Celsius) String() string {
    return fmt.Sprintf("%.1f°C", float64(t))
}
```

You cannot define a method on a type from another package — for example, `func (t time.Time) Weekday2() string { ... }` fails with `cannot define new methods on non-local type time.Time` — but wrapping it in a local named type is always allowed.

## Method sets

The **method set** of a type determines which interfaces it satisfies:

- The method set of `T` contains all methods with value receiver `(t T)`.
- The method set of `*T` contains all methods — both `(t T)` and `(t *T)`.

This is why an interface requiring a pointer-receiver method can only be satisfied by `*T`, not by `T`.

## Addressability: when method sets bite

Calling a pointer-receiver method on a value auto-takes its address — `c.Inc()` on a variable `c` really means `(&c).Inc()`. But Go can only take that address when `c` is **addressable**: a plain variable, a struct field of an addressable struct, or `*p` for some pointer `p`. Two everyday values are **not** addressable — a map value, and the result of a composite literal used directly.

```go
type Counter struct{ count int }

func (c *Counter) Inc() { c.count++ }

func main() {
	m := map[string]Counter{"a": {}}
	m["a"].Inc() // map values are not addressable
}
```

Compiling this with Go 1.26.5 gives:

```text
./main.go:15:9: cannot call pointer method Inc on Counter
```

The reason is structural: a map can rehash and move its entries at any time, so Go refuses to hand out a stable address into it. The fix is either to store pointers (`map[string]*Counter`) or to copy out, mutate, and store back.

The same error appears for a composite literal used directly, because a literal has no variable to take the address of:

```go
Counter{}.Inc()
```

```text
./main.go:12:12: cannot call pointer method Inc on Counter
```

Addressability also decides interface satisfaction. `T`'s method set only has value-receiver methods, so assigning a `T` value to an interface that needs a pointer-receiver method fails at compile time, not at the call:

```go
type Incer interface{ Inc() }

var i Incer = Counter{}
```

```text
./main.go:16:16: cannot use Counter{} (value of struct type Counter) as Incer value in variable declaration: Counter does not implement Incer (method Inc has pointer receiver)
```

`var i Incer = &Counter{}` compiles, because `*Counter`'s method set includes `Inc`.

## Method values vs method expressions

A **method value** — `c.Inc` — is a function bound to the specific receiver `c` at the moment you take it. A **method expression** — `Counter.Value` — takes the type itself, and the receiver becomes the function's first parameter:

```go
c := &Counter{}
inc := c.Inc     // bound to c already — inc() means c.Inc()
inc()

value := Counter.Value // unbound — receiver is the first argument
fmt.Println(value(*c))
```

Method values are handy for passing a bound method as a callback (`http.HandleFunc("/x", h.serveX)`); method expressions are rare, mostly seen in generic code that needs to call a method on a type parameter's underlying type.

## Nil pointer receivers

Calling a method through a nil pointer is legal in Go, as long as the method body never dereferences a nil field before checking for it. This is the standard way to write a recursive nil-safe method on a linked structure:

```go
type List struct {
	val  int
	next *List
}

func (l *List) Sum() int {
	if l == nil {
		return 0
	}
	return l.val + l.next.Sum()
}
```

`var l *List; l.Sum()` returns `0` without panicking — the method call itself does not dereference `l`, and the body's own nil check handles it.

## Receiver naming

Idiomatic Go receivers are one or two letters derived from the type name — `c Counter`, `r *Rectangle` — never `this` or `self`. Keep the same receiver name for every method on a type; the standard library follows this throughout (`func (b *Buffer) WriteString`, `func (t Time) Add`).

## Methods on a named function type

Because any named type can have methods, a named function type can too. The standard library uses this to turn a plain function into something that satisfies an interface — `http.HandlerFunc` is a `func(http.ResponseWriter, *http.Request)` with a `ServeHTTP` method, which is the only thing `http.Handler` requires:

```go
type IntOp func(int) int

func (f IntOp) Twice(x int) int {
	return f(f(x))
}
```

`IntOp(double).Twice(3)` calls `double` on its own result — the function itself is the receiver.

## Copying a mutex: the value-receiver trap

`sync.Mutex` must never be copied after first use, because a copy has its own independent lock state. A value receiver copies the whole struct on every call — so a value-receiver method on a struct containing a mutex silently locks a copy, protecting nothing:

```go
type Safe struct {
	mu    sync.Mutex
	count int
}

func (s Safe) Inc() { // value receiver — copies mu on every call
	s.mu.Lock()
	defer s.mu.Unlock()
	s.count++
}
```

`go vet` catches this exact bug:

```text
main.go:11:9: Inc passes lock by value: command-line-arguments.Safe contains sync.Mutex
```

The fix is always a pointer receiver: `func (s *Safe) Inc()`. Any struct holding a `sync.Mutex`, `sync.WaitGroup`, or similar must use pointer receivers on every method, and should never be passed or returned by value.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Value receiver | Cheap to reason about, callable on non-addressable values | Copies the struct on every call |
| Pointer receiver | Can mutate, no copy | Needs a nil-check, receiver must be addressable |
| Method on a non-struct type | Extends the behavior of any named type in your package | Cannot add a method to a type from another package |
| Method value | Bundles a receiver with a function, easy to pass as a callback | Keeps the receiver alive for the closure's lifetime |
| Pointer receiver on a type holding a mutex | The only correct option | Every method — even read-only ones — must take a pointer |

## Common Misconceptions

- **Value and pointer receivers are interchangeable.** A value receiver works on a copy — it cannot mutate the caller's original value.
- **You can add a method to a type from another package.** Go does not allow this; wrap the type in a local named type or use embedding instead.
- **`T` and `*T` have the same method set.** `*T`'s method set is larger — it also includes the pointer-receiver methods, which affects interface satisfaction.
- **A map value with a pointer-receiver method just works, like a struct variable.** It does not — map values are not addressable, so `m[k].Inc()` is a compile error, not a runtime surprise.
- **Copying a struct that embeds `sync.Mutex` is harmless if you don't `Lock` right away.** The copy is already broken the moment it exists; `go vet` flags the copy itself, not just the lock call.

> 💡 Real-world example
>
> `net/http`: `http.ResponseWriter` is an interface — every `Handler` accepts it instead of a concrete type, which makes handlers easy to test with a mock. `http.HandlerFunc` is a named function type with a `ServeHTTP` method, so a plain function can satisfy `http.Handler` with a one-line conversion.
>
> `*bytes.Buffer` and `*http.Client` both use a pointer receiver on every method because they hold internal state that methods mutate (buffered bytes, a connection pool) — consistency of receiver kind matters here.

## Reading AI-generated code

When a generated snippet defines methods, check for these before trusting it:

- Does every method on the type use the *same* receiver kind — all value, or all pointer? A mix is a warning sign.
- If a method mutates a field, is the receiver a pointer? A value-receiver mutation compiles and silently does nothing.
- Does the type's struct contain a `sync.Mutex`, `sync.WaitGroup`, or similar? Every method must be a pointer receiver, and the type must never be copied or passed by value.
- Is a pointer-receiver method ever called on a map value (`m[k].Method()`) or a fresh composite literal (`T{}.Method()`)? Both fail to compile — addressability, not a runtime bug.
- Does an interface variable get assigned a value type (`var i Iface = T{}`) when the required method has a pointer receiver? That's a compile error the generated code may have never actually been run against.

<Callout title="Use a pointer receiver when you need to mutate — and be consistent">
A value receiver always operates on a copy, so mutations are silently discarded. Use a pointer receiver whenever a method must change the receiver's state. Once you choose pointer receivers for any method on a type, use them for all methods on that type to keep the method set coherent and avoid surprising interface-satisfaction gaps.
</Callout>
