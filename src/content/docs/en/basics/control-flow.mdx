## if statements

A basic `if` in Go looks familiar, but parentheses around the condition are omitted — the braces are always required:

```go
if x > 0 {
    fmt.Println("positive")
}
```

Go adds an **init statement** separated by a semicolon before the condition. Variables declared in the init are scoped to the entire `if/else` block:

```go
if err := doWork(); err != nil {
    fmt.Println("error:", err)
    return
}
// err is not in scope here
```

This pattern is idiomatic for operations that return `(value, error)` — it keeps the error variable close to the check and avoids polluting the outer scope.

## for — Go's only loop

Go has **one loop keyword**: `for`. It covers all three common loop shapes.

**C-style loop** — init; condition; post:

```go
for i := 0; i < 5; i++ {
    fmt.Println(i)
}
```

**Condition-only loop** (equivalent to `while` in other languages):

```go
n := 1
for n < 100 {
    n *= 2
}
```

**Infinite loop** — omit the condition entirely; use `break` to exit:

```go
for {
    if done() {
        break
    }
}
```

## for range

`range` iterates over arrays, slices, strings, maps, and channels. It returns an index and a value on each iteration:

```go
fruits := []string{"apple", "banana", "cherry"}
for i, v := range fruits {
    fmt.Println(i, v)
}

// Discard the index with _
for _, v := range fruits {
    fmt.Println(v)
}

// Range over a string yields runes (Unicode code points), not bytes
for i, r := range "Go!" {
    fmt.Printf("%d: %c\n", i, r)
}
```

Since Go 1.23, `range` can also drive a `for` loop over a function with a special signature — this is the basis of the `iter` package and custom iterators, covered fully in Iterators once you have seen more of the type system.

## Range over an integer, and per-iteration loop variables

Since Go 1.22 `range` also accepts an integer, which replaces the classic counting loop when you only need the index:

```go
for i := range 5 {        // 0, 1, 2, 3, 4
    fmt.Println(i)
}
for range 3 {             // repeat three times, no variable
    fmt.Println("tick")
}
```

Go 1.22 also changed loop-variable semantics: each iteration gets a **fresh** `i` (and `v`), so closures and goroutines started inside the loop no longer all see the final value. The old `i := i` copy is unnecessary in modules with `go 1.22` or later in `go.mod` — the full before/after comparison, with real output from both, is in Functions.

## Labeled `break` and `continue`

A `break` or `continue` normally applies to the innermost `for`. A **label** — an identifier followed by a colon, placed on the line before a `for` — lets you name that loop and target it from a nested loop:

```go
outer:
for i := 0; i < 3; i++ {
    for j := 0; j < 3; j++ {
        if j == 1 {
            continue outer // skip to the next i, not the next j
        }
        if i == 2 {
            break outer // exit both loops entirely
        }
        fmt.Println(i, j)
    }
}
```

`continue outer` skips the rest of the inner loop *and* the rest of that iteration of the outer loop; `break outer` exits both loops immediately.

## `break` inside `switch` or `select` doesn't exit the loop

This is one of the most common bugs in generated Go code. A bare `break` exits the **innermost enclosing `switch` or `select`**, not an outer `for` — even though the loop is the thing most people mean to stop:

```go
for i := 0; i < 3; i++ {
    switch i {
    case 1:
        break // exits only this switch — the loop keeps going
    default:
        fmt.Println("processing", i)
    }
}
```

This prints `processing 0` and `processing 2` — `case 1` runs its `break`, which does nothing except leave the `switch`, and the `for` loop happily continues to `i = 2`. The same rule applies to a `select` inside a `for` (covered in the concurrency module once channels are introduced): a `break` in one of its cases only leaves the `select`. To actually stop the loop, label it and break the label:

```go
loop:
for i := 0; i < 5; i++ {
    switch {
    case i == 3:
        break loop // this one really does exit the for
    default:
        fmt.Println(i)
    }
}
```

## `range` copies elements, and evaluates its expression once

Two behaviors of `range` surprise newcomers, and both matter when reading generated code:

**It copies each element into the loop variable.** Mutating that variable never changes the underlying collection:

```go
nums := []int{1, 2, 3}
for _, v := range nums {
    v *= 10 // modifies the local copy only
}
fmt.Println(nums) // [1 2 3] — unchanged
```

**It evaluates the ranged expression exactly once, at the start of the loop.** For a slice, that means the loop bound is fixed to the slice's length *at that moment* — appending to the slice inside the loop body does not make the loop visit the new elements:

```go
s := []int{1, 2, 3}
for i, v := range s {
    if i == 0 {
        s = append(s, 4) // extends s, but range already captured the original length
    }
    fmt.Println(i, v)
}
// loop body still only runs for i = 0, 1, 2 — the appended 4 is never visited
```

## switch

Go's `switch` evaluates cases top to bottom and **stops at the first match** — there is no automatic fallthrough to the next case. You do not need `break` at the end of each case:

```go
switch day {
case "Monday", "Tuesday", "Wednesday", "Thursday", "Friday":
    fmt.Println("weekday")
case "Saturday", "Sunday":
    fmt.Println("weekend")
default:
    fmt.Println("unknown")
}
```

Like `if`, `switch` accepts an **init statement** before the condition, scoped to the whole switch — handy for computing the value you are branching on right at the switch itself:

```go
switch x := score(); {
case x > 10:
    fmt.Println("big")
case x > 5:
    fmt.Println("medium")
default:
    fmt.Println("small")
}
```

**Switch-true** (expressionless switch, as used above) acts as a cleaner if/else chain, with each case an independent boolean expression. To match multiple values in one case, list them comma-separated.

## Fallthrough's limits

To fall through to the next case explicitly, use `fallthrough` as the last statement in a case. It is unconditional — it runs the next case's body regardless of that case's own condition:

```go
switch x := score(); {
case x > 10:
    fmt.Println("big")
    fallthrough
case x > 5:
    fmt.Println("medium-or-big") // runs even though this case's own test was never evaluated
default:
    fmt.Println("other")
}
```

`fallthrough` has two hard limits the compiler enforces. It cannot appear in the **last** case of a switch:

```text
./main.go:9:3: cannot fallthrough final case in switch
```

And it cannot be used at all in a **type switch**:

```text
./main.go:10:3: cannot fallthrough in type switch
```

## A one-sentence `goto`

`goto` jumps to a labeled statement in the same function and exists mainly for generated code and rare cleanup patterns; idiomatic hand-written Go almost never uses it, reaching for a labeled loop, an early `return`, or a restructured function instead.

## Trade-offs

| What you get | Benefit | Cost |
|---------------|---------|------|
| One `for` keyword | Less to learn, consistent code | You must remember the three forms (C-style, condition-only, infinite) |
| `for range` | Reads cleanly, no manual index bookkeeping | `range` copies each element's value and evaluates its expression once — both surprise code that mutates in place or appends mid-loop |
| `switch` with no automatic fallthrough | Fewer bugs from a forgotten `break` | You must write `fallthrough` explicitly on the rare occasion you want it, and it cannot appear in the last case or a type switch |
| `if`/`switch` init statement | The `err` variable's scope stays as narrow as possible | The syntax looks unusual to developers coming from other languages |
| Labeled break/continue | Precise control over which loop a jump targets | An unlabeled `break` inside a `switch`/`select` inside a `for` is a classic, silent bug |

## Common Misconceptions

- **"`range` copies the whole slice."** `range` only copies the value of each element, not the whole slice — and the slice header itself is evaluated only once, at the start of the loop.
- **"Go `for` loops always need semicolons like C."** `for i := 0; i < n; i++` uses semicolons, but `for range` and the condition-only loop do not.
- **"`break` inside a `switch` that's inside a `for` stops the loop."** It only exits the `switch` (or `select`) — the loop keeps running. Reach for a labeled `break` when you actually mean to stop the loop.
- **"Appending to a slice while ranging over it makes the loop see the new elements."** It does not — `range` evaluates the slice's length once, before the first iteration.

## Reading AI-generated code

Control-flow bugs are some of the easiest for generated code to hide, because the program still compiles and often still runs — it just does the wrong number of iterations or exits the wrong thing:

- Is there a bare `break` inside a `switch` (or `select`) that itself sits inside a `for`? Check whether the intent was to stop the loop — if so, it needs a label.
- Does a `for range` loop mutate its value variable (`for _, v := range s { v = ... }`) expecting the source slice to change? It never will.
- Does a loop `append` to the very slice it is ranging over, expecting to visit the newly appended elements? `range` already fixed the iteration count before the first append ran.
- Does a `fallthrough` sit in what turns out to be the last case, or inside a type switch? Both are compile errors, not runtime surprises.
- Is a labeled `continue`/`break` used where a plain one was intended, or vice versa — check which loop the label actually names.

<Callout title="`for` is Go's only loop keyword">
Go has no `while`, `do-while`, `until`, or `loop` keyword. Every iteration — whether bounded, conditional, or infinite — uses `for`. The three forms (C-style; condition-only; no-condition) cover every pattern. If you want a `while` loop, write `for condition` with the init and post omitted. This deliberate constraint keeps the language smaller and every loop form immediately recognisable.
</Callout>
