## Function basics

A Go function declares its parameter types and return types explicitly. The return type appears after the parameter list:

```go
func add(a int, b int) int {
    return a + b
}

// Consecutive parameters of the same type can share a type annotation.
// This is a second, equivalent spelling of the same function — pick one style per function.
func add(a, b int) int {
    return a + b
}
```

Every argument in Go is passed **by value** — a copy of it — with no exception. That is easy to see for an `int` or a `struct`, but it is true for a slice too: a slice argument copies its small three-word header (pointer, length, capacity), not the backing array. That is why writing to `s[i]` inside a function is visible to the caller, while `append`-ing inside the function sometimes is not — the full explanation, with the header diagram, is in Slices.

## Multiple return values

Go functions can return more than one value. The idiomatic pattern is `(result, error)` — the caller must handle or explicitly discard the error:

```go
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}

result, err := divide(10, 3)
if err != nil {
    log.Fatal(err)
}
fmt.Println(result)
```

## Named return values

Return values can be named. Named returns pre-declare variables and allow a **bare return** (a `return` with no arguments that returns the current values of the named variables). Use them sparingly — they are clearest in short functions where the names genuinely document the result:

```go
func bounds(nums []int) (lo, hi int) {
    lo, hi = nums[0], nums[0]
    for _, v := range nums[1:] {
        if v < lo {
            lo = v
        }
        if v > hi {
            hi = v
        }
    }
    return // bare return: returns current lo, hi
}
```

Naming named results `min` and `max` would also compile — Go 1.21's built-in `min`/`max` functions can be shadowed by a local name — but it is a smell: it hides the built-ins from the rest of the function body for no benefit.

## Variadic functions

A variadic function accepts a variable number of arguments of the same type. Declare the last parameter with `...`:

```go
func sum(nums ...int) int {
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}

sum(1, 2, 3)        // individual args
sum([]int{1,2,3}...) // spread a slice with ...
```

Inside the function, `nums` is a `[]int` slice. Spreading a `nil` slice works too and is not a special case: `var none []int; sum(none...)` passes an empty slice, and the loop simply runs zero times, returning `0`. A `nil` slice behaves like a zero-length one everywhere it is read.

## `defer`

`defer` schedules a function call to run **when the surrounding function returns**, regardless of which return path is taken. It is the idiomatic way to clean up resources:

```go
func readFile(name string) error {
    f, err := os.Open(name)
    if err != nil {
        return err
    }
    defer f.Close() // runs when readFile returns

    // ... work with f ...
    return nil
}
```

Multiple deferred calls execute in **LIFO order** (last deferred, first to run).

**Arguments to a deferred call are evaluated immediately, at the `defer` statement** — not when the deferred call actually runs:

```go
i := 0
defer fmt.Println(i) // captures i's value (0) right now
i = 100
// when the function returns, this prints "0", not "100"
```

## `defer` and named results

A deferred closure can read and even *rewrite* a named return value, because the named result is just a variable in scope for the whole function body — including its deferred calls. This is the standard way to annotate or transform an error right before it leaves a function:

```go
func doWork() (err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("doWork: %w", err)
        }
    }()
    return errors.New("boom")
}
```

`doWork()` returns `errors.New("boom")`, but by the time the caller sees it, the deferred function has already run and wrapped it — the call prints `doWork: boom`. This only works with a *named* result: a deferred function closing over a plain `return err` cannot change what the caller receives, because there is no shared variable for it to modify.

## `defer` inside a loop

`defer` runs at function return, not at the end of the loop iteration it was written in. Deferring inside a `for` loop is a classic source of resource leaks — every file, connection, or lock accumulates until the whole function exits, not each time around the loop:

```go
func leaky(n int) {
    for i := 0; i < n; i++ {
        r := openResource(i)
        defer r.Close() // accumulates n deferred calls, all pending until leaky returns
    }
    // if n is large, this line runs with n resources still open
}
```

If `leaky` is itself a long-running function — say, one that processes thousands of files in a loop — every open file descriptor stays open until the very end, and the process can run out of them long before `leaky` returns. The fix is to give each iteration its own scope, typically a helper function, so `defer` fires per iteration:

```go
func tidy(n int) {
    for i := 0; i < n; i++ {
        func() {
            r := openResource(i)
            defer r.Close() // runs at the end of this anonymous function, every iteration
            // ... use r ...
        }()
    }
}
```

A closely related bug is `defer f.Close()` silently discarding the error `Close` returns. For a read-only file this is usually harmless, but for a file you *wrote to*, `Close` can be the call that actually flushes buffered data — and a failed flush is a real error you just threw away:

```go
func saveBuggy(f *os.File, data []byte) error {
    defer f.Close() // any error from Close is silently discarded
    _, err := f.Write(data)
    return err
}

func saveFixed(f *os.File, data []byte) (err error) {
    defer func() {
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr // only report Close's error if Write didn't already fail
        }
    }()
    _, err = f.Write(data)
    return err
}
```

## Closures and first-class functions

Functions are first-class values in Go. You can assign them to variables, pass them as arguments, and return them from other functions:

```go
double := func(n int) int { return n * 2 }
fmt.Println(double(5)) // 10

// Function as a parameter
apply := func(f func(int) int, x int) int { return f(x) }
fmt.Println(apply(double, 3)) // 6
```

A **closure** is a function that captures variables from its enclosing scope. The captured variable is shared — the closure sees mutations to it:

```go
func counter() func() int {
    n := 0
    return func() int {
        n++
        return n
    }
}

c := counter()
fmt.Println(c()) // 1
fmt.Println(c()) // 2
fmt.Println(c()) // 3
```

Each call to `counter()` creates an independent `n`, so two counters do not interfere with each other.

## Closures over loop variables: before and after Go 1.22

A closure created inside a `for` loop captures the loop variable itself, not a snapshot of its value at that iteration. Before Go 1.22, all iterations of a `for` shared **one** variable, so every closure ended up seeing whatever the variable held when it was finally called:

```go
var fns []func()
for _, v := range []int{0, 1, 2} {
    fns = append(fns, func() { fmt.Println(v) })
}
for _, f := range fns {
    f()
}
```

Compiled with `go 1.21` in `go.mod`, this program prints `2 2 2` on Go 1.26.5 — every closure shares the same `v`, whose final value after the loop is `2`. The traditional fix, still common in code written before 1.22 (and in anything an AI trained on that code produces), is to make a fresh copy inside the loop body: `v := v` before using `v` in the closure.

Go 1.22 changed the semantics: each iteration gets its **own** `v`, so the same source line — with only `go.mod`'s `go` directive changed to `1.22` — prints `0 1 2`:

```text
go 1.21 in go.mod → 2
                     2
                     2

go 1.22 in go.mod → 0
                     1
                     2
```

Both lines above are real output from this exact program on Go 1.26.5, changing only the `go` line in `go.mod` between runs. The interactive playground below always targets a modern toolchain, so it will show the post-1.22 behavior; the `go` directive is what gates this change, per module, and it cannot be toggled from inside a single program. The `v := v` copy is unnecessary once a module's `go.mod` says `go 1.22` or later — but you will still see it in older code, and recognizing it tells you the author was guarding against the old behavior.

## Function values, method values, and nil

A function type is just another type — you can declare a variable of it, store it in a struct field, or pass it as a value. Its zero value is `nil`, and a function value can only ever be compared against `nil` (comparing two non-nil function values with `==` is a compile error):

```go
type IntFunc func(int) int

var f IntFunc
fmt.Println(f == nil) // true

f(3) // panics: runtime error: invalid memory address or nil pointer dereference
```

This is the same shape of bug as a nil pointer dereference, and it shows up most often with optional callback fields on a struct (`OnError func(error)`) that a caller forgot to set. Always nil-check a function value before calling it unless the type's contract guarantees it is always set.

## Trade-offs

| What you get | Benefit | Cost |
|---------------|---------|------|
| Multiple return values | Explicit error handling, no hidden exceptions | The caller must check every error — more verbose than try/catch |
| Named return values | Documents intent in the signature, enables bare return, lets `defer` rewrite the result | A bare return in a long function makes it harder to read |
| `defer` | Cleanup code sits right next to resource acquisition | Arguments are evaluated immediately, LIFO order can surprise you, and it runs at function exit, not loop-iteration exit |
| Closures | Encapsulate state concisely | Captured variables are often allocated on the heap (escape analysis) |
| Pass-by-value everywhere | No hidden aliasing through function boundaries by default | Passing a large struct by value copies all of it; a slice or map argument still lets you mutate what it points to |

## Common Misconceptions

- **"`defer` is slow."** `defer` has very low overhead (nanosecond range) — it is safe to use in production code for cleanup.
- **"Multiple return values hurt performance."** Go returns multiple values directly via registers or the stack, with no heap allocation — the performance impact is negligible.
- **"Every closure escapes to the heap."** The compiler performs escape analysis and may allocate a closure on the stack if it never escapes its scope.
- **"Functions in Go are not first-class."** Functions in Go are first-class values — you can assign them, pass them as arguments, or return them from other functions.
- **"`defer` inside a loop cleans up each iteration."** It does not — every deferred call is pending until the *enclosing function* returns, not the loop.

## Reading AI-generated code

When a generated function uses `defer`, closures, or function values, check these before trusting it:

- Does a `defer` sit inside a `for` loop that can run more than a couple of times? Every iteration's deferred call stays pending until the function returns, not the loop.
- Does `defer f.Close()` follow a `Write`/`Flush`-style call, discarding whatever error `Close` returns? Look for a named result the deferred func could attach that error to instead.
- Does a closure capture a loop variable, and if so, does the module's `go.mod` declare `go 1.22` or later? Below that, every closure created in the loop shares one variable.
- Is a function-typed value (a field, a parameter) called without checking it against `nil` first?
- Does the code compare two function values directly with `==` (not against `nil`)? That is a compile error — function types support no other comparison.

<Callout title="Deferred calls run LIFO at return">
Multiple `defer` statements in the same function execute in **last-in, first-out** order when the function returns. This mirrors a stack: the last thing you deferred is the first thing that runs on the way out. Importantly, **arguments are evaluated at the defer site**, not when the deferred call actually executes — so `defer fmt.Println(x)` captures the current value of `x`, even if `x` changes before the function returns. A deferred closure is the exception: it can still read (and, for a named result, rewrite) variables at the moment it actually runs.
</Callout>
