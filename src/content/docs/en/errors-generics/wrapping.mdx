## Why wrap errors?

When a function calls another and it fails, returning the raw error loses context. The caller sees "database error" but has no idea which operation triggered it, which request it belonged to, or at what layer it occurred. Wrapping adds a layer of context — what were you trying to do? — while preserving the original error so it can still be inspected.

The idiomatic pattern in Go:

```go
if err != nil {
    return fmt.Errorf("description: %w", err)
}
```

The `%w` verb is the key. It wraps the original error inside the new one, keeping the full chain intact for callers who need to inspect it.

## fmt.Errorf and %w

`fmt.Errorf` creates a new error whose message incorporates other values — but how it incorporates an error argument depends on the verb you choose:

- **`%v`** formats the error's message string and embeds it as plain text. The original error type is gone. The chain is cut.
- **`%w`** records the original error by value inside the new error. The message still contains the original message, but the original is also accessible programmatically.

```go
base := errors.New("connection refused")

// %v — message only, chain is severed
e1 := fmt.Errorf("dial: %v", base)
fmt.Println(errors.Is(e1, base)) // false

// %w — wraps, chain is preserved
e2 := fmt.Errorf("dial: %w", base)
fmt.Println(errors.Is(e2, base)) // true
```

Use `%w` when you want callers upstream to be able to identify or extract the original error. Use `%v` only when you intentionally want to discard the error type — for example, when logging and the chain is irrelevant.

## errors.Is — checking identity through a chain

`errors.Is(err, target)` walks the entire unwrap chain of `err` and returns `true` if any error in the chain matches `target`. Matching is done by identity (`==`) by default, not by message string.

```go
var ErrNotFound = errors.New("not found")

err := fmt.Errorf("getUser: %w", fmt.Errorf("queryDB: %w", ErrNotFound))

fmt.Println(errors.Is(err, ErrNotFound)) // true — found deep in the chain
```

This works regardless of how deeply the target is nested. You define a sentinel error once (a package-level `var`) and check for it anywhere in the call stack.

## errors.As — extracting a type from the chain

`errors.As(err, &target)` also walks the chain, but instead of checking identity, it checks type. If any error in the chain can be assigned to `target`'s type, it performs the assignment and returns `true`.

```go
var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println(ve.Field) // access fields on the concrete type
}
```

Use `errors.As` when you have a custom error type that carries extra information — field names, HTTP status codes, retry hints — and you need to access those fields, not just check that the error exists.

### `errors.AsType` — the generic form (Go 1.26)

Go 1.26 added `errors.AsType[T]`, a type-safe alternative to `errors.As`. It returns the matched value and a bool, so there is no pointer-to-pointer argument to get wrong and the compiler checks `T`:

```go
if ve, ok := errors.AsType[*ValidationError](err); ok {
    fmt.Println(ve.Field)
}
```

Prefer `AsType` in new code; `errors.As` remains for older toolchains. (`go fix` can migrate existing call sites.)

## Custom error types

Any struct that implements `Error() string` satisfies the `error` interface. Custom types let you carry structured context alongside the message:

```go
type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation: field %q %s", e.Field, e.Message)
}
```

To make a custom error type part of a wrapping chain, implement `Unwrap() error`:

```go
type AppError struct {
    Code int
    Err  error
}

func (e *AppError) Error() string  { return fmt.Sprintf("code %d: %v", e.Code, e.Err) }
func (e *AppError) Unwrap() error  { return e.Err }
```

With `Unwrap` in place, `errors.Is` and `errors.As` can see through `AppError` to reach whatever it wraps.

## errors.As needs a pointer to the concrete type

`errors.As(err, target)`'s second argument must be a non-nil pointer to a variable whose type either implements `error` or is an interface. Get this wrong and `errors.As` panics instead of returning `false` — a deliberate choice, since a bad target is almost always a coding mistake, not a runtime condition worth silently ignoring.

The single most common version of this mistake is passing the pointer variable itself instead of its address:

```go
var ve *VErr
errors.As(err, ve) // BUG: passing ve, not &ve
```

Verified on 1.26.5, this panics:

```
panic: errors: target must be a non-nil pointer
```

`ve` is a nil `*VErr`. Passing it directly hands `errors.As` a pointer of the right *kind* but no addressable storage to write a match into — `errors.As` needs `&ve` (a `**VErr`) so it has somewhere to store the result. A target whose pointee type doesn't implement `error` at all panics with a different, equally real message:

```go
var n int
errors.As(err, &n) // BUG: *int does not implement error
```
```
panic: errors: *target must be interface or implement error
```

## errors.Join and multiple %w

`errors.Join` (Go 1.20) combines several errors into one value whose `Unwrap() []error` method exposes all of them. `errors.Is` and `errors.As` walk every branch, so a single `errors.Is` call can match any of the joined errors:

```go
joined := errors.Join(ErrDisk, ErrNet)
fmt.Println(errors.Is(joined, ErrDisk)) // true
fmt.Println(errors.Is(joined, ErrNet))  // true
```

`fmt.Errorf` accepts more than one `%w` in the same call, also since Go 1.20, which produces the same kind of multi-error chain:

```go
err := fmt.Errorf("save failed: %w, %w", ErrDisk, ErrNet)
```

Both forms mean `errors.Unwrap(err)` — which only understands the single-error `Unwrap() error` shape — returns `nil` for them. Use `errors.Is`/`errors.As` to inspect a joined or multi-`%w` error; never assume `errors.Unwrap` alone will reach every branch.

## Custom Is and As methods

`errors.Is` and `errors.As` check for an `Is(target error) bool` or `As(target any) bool` method on each error in the chain before falling back to their default identity/type check. This lets a type override what counts as a match:

```go
// Is lets errors.Is treat every ValueErr as equal, regardless of msg --
// useful when the exact message varies but the caller only cares
// "was it this kind of error?"
func (e ValueErr) Is(target error) bool {
	_, ok := target.(ValueErr)
	return ok
}
```

With this method in place, `errors.Is(err, ValueErr{msg: "anything"})` reports `true` for *any* `ValueErr` in the chain, not just one with an identical `msg` field. Define a custom `As` the same way when the default type-match isn't precise enough — for example, to match against an underlying error code stored in a field rather than the wrapper's own type.

## Receiver choice affects errors.As

The concrete type that ends up in the error chain is whatever type actually implements `error` — and that depends on the receiver you chose. A pointer receiver means only `*T` implements `error`, so the chain holds `*T` and `errors.As` needs a `**T` target. A value receiver means `T` implements `error` directly, and wrapping a `T` value (not `&T{}`) puts a `T` in the chain — `errors.As` with a `**T` target finds nothing:

```go
perr := fmt.Errorf("op: %w", &PtrErr{Code: 7}) // *PtrErr in the chain
var asPtr *PtrErr
errors.As(perr, &asPtr) // true

err := fmt.Errorf("op: %w", ValueErr{msg: "x"}) // ValueErr in the chain
var asValuePtr *ValueErr
errors.As(err, &asValuePtr) // false -- chain holds ValueErr, not *ValueErr
var asValue ValueErr
errors.As(err, &asValue) // true -- matches the value type
```

There is nothing wrong with either receiver choice on its own; the bug is writing the `errors.As` target as if the error had been wrapped as a pointer when it was wrapped as a value, or vice versa.

## %w with a nil error

Wrapping a nil error is legal — `fmt.Errorf` does not panic — but it produces a message you almost certainly did not intend:

```go
var inner error // nil
err := fmt.Errorf("op failed: %w", inner)
fmt.Println(err) // op failed: %!w(<nil>)
```

`%w` requires a non-nil `error` argument to record; handed `nil`, `fmt` falls back to its usual bad-verb formatting and embeds `%!w(<nil>)` in the message. `go vet`'s `printf` check cannot catch this case — `inner`'s static type is `error`, and vet has no way to know its value is `nil` at compile time. Guard with `if err != nil` before wrapping, the same discipline used everywhere else.

## No stack traces

The standard `errors` package never records where an error was created or which goroutine touched it — `Error()` returns a string, and that is the entire contract. Wrapping with `%w` builds a chain of *messages and causes*, not a call stack. When you need positional information, you add it explicitly: capture `runtime.Caller` or `runtime/debug.Stack()` at the point of creation and store it as a field, or reach for a third-party package built for this (`github.com/pkg/errors` popularized `errors.WithStack`, predating `errors.Is`/`errors.As` in the standard library). This is a deliberate trade-off — cheap, composable errors that cost nothing until you decide you need more.

## Reading AI-generated code

When a generated snippet calls `errors.As` or wraps multiple errors, check for these before trusting it:

- Is `errors.As` called with the pointer variable itself (`errors.As(err, ve)`) instead of its address (`errors.As(err, &ve)`)? The first form panics at runtime; it never just returns `false`.
- Does code call `errors.Unwrap(err)` expecting to reach every error inside an `errors.Join` or multi-`%w` result? `Unwrap() []error` is a different shape — only `errors.Is`/`errors.As` walk it.
- Does a custom error type's receiver (value vs pointer) match the pointer-ness of every `errors.As` target used against it elsewhere in the codebase?
- Does `fmt.Errorf("...: %w", err)` ever run when `err` could be `nil`? Check the caller, not just the line itself — `go vet` will not flag this.
- Does the code assume errors carry a stack trace or line number by default? The standard library never attaches one.

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| fmt.Errorf("%w", err) | wraps with context, errors.Is/As work | more verbose than a bare `return err` |
| errors.Is() through the chain | matches a sentinel at any depth | slower than `==` (has to traverse the chain) |
| custom error type | carries structured context (field, code, status) | you must maintain the type and implement Error() |
| %v vs %w in fmt.Errorf | %v shows the message as a string, %w preserves the chain | easy to confuse the two verbs |

## Common Misconceptions

- **wrapping an error at every layer always adds useful context** — wrapping too deeply makes the error message hard to read; only wrap when the caller actually needs that context.
- **errors.Unwrap walks the whole chain for you** — actually `errors.Unwrap` strips off only **one** wrapper per call, and returns `nil` for an error whose method is `Unwrap() []error` rather than `Unwrap() error` — for example the result of `errors.Join` or an `fmt.Errorf` with more than one `%w`. To walk the whole chain or find a match, use `errors.Is`/`errors.As` instead.
- **%w in fmt.Errorf only supports one error** — Go 1.20+ supports `fmt.Errorf("msg: %w and %w", e1, e2)` to wrap multiple errors.
- **errors.Is compares the message string** — errors.Is checks identity (`==`), not the message string — sentinel errors must be package-level vars.

<Callout title="Wrap to add context; use errors.Is/As to inspect">
Use `%w` (not `%v`) when you want callers to be able to introspect the error chain. `errors.Is` checks identity (sentinel errors). `errors.As` checks type (structured errors with fields). Use `%v` only when you are discarding the original error type on purpose.
</Callout>
