## The io.Reader and io.Writer interfaces

The `io` package defines two small but foundational interfaces:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

These two interfaces are the lingua franca of I/O in Go. Dozens of types implement them: files, network connections, HTTP request and response bodies, in-memory buffers, and more. Functions that accept `io.Reader` or `io.Writer` work with all of them without modification.

## strings.NewReader — an in-memory Reader

`strings.NewReader(s)` wraps a string as an `io.Reader`. This is invaluable in tests and examples — you can exercise any function that reads from a stream without touching the filesystem.

```go
r := strings.NewReader("hello, world")
data, _ := io.ReadAll(r)
fmt.Println(string(data)) // hello, world
```

## bytes.Buffer — a read/write buffer

`bytes.Buffer` implements both `io.Reader` and `io.Writer`. You write into it and read back out:

```go
var buf bytes.Buffer
fmt.Fprintln(&buf, "first line")
fmt.Fprintln(&buf, "second line")
content, _ := io.ReadAll(&buf)
fmt.Print(string(content))
```

`fmt.Fprintln` accepts any `io.Writer`, so you can redirect formatted output to a buffer, a file, or a network connection with zero code changes.

## bufio.Scanner — line-by-line reading

`bufio.Scanner` wraps any `io.Reader` and provides convenient line-by-line (or token-by-token) reading. The default split function is `bufio.ScanLines`.

```go
scanner := bufio.NewScanner(r)
for scanner.Scan() {
    fmt.Println(scanner.Text()) // one line at a time
}
if err := scanner.Err(); err != nil {
    log.Fatal(err)
}
```

`scanner.Scan()` returns `false` when the input is exhausted or an error occurs. Always check `scanner.Err()` after the loop — a `false` return alone does not distinguish EOF from an error.

## io helper functions

The `io` package also provides useful helpers:

```go
io.ReadAll(r)           // read until EOF, return []byte
io.Copy(dst, src)       // copy from Reader to Writer
io.MultiReader(r1, r2)  // chain readers sequentially
io.Discard              // Writer that discards all bytes (like /dev/null)
io.LimitReader(r, n)    // read at most n bytes
```

## The io.Reader contract in depth

The two-line `Read(p []byte) (n int, err error)` signature hides three rules that trip up AI-generated code constantly:

1. **`Read` can return `n > 0` and a non-nil `err` in the same call.** The caller must process the `n` bytes returned *before* checking `err` — discarding them because `err != nil` silently drops the last chunk of data.
2. **A "short read" is legal.** `Read` may fill fewer bytes than `len(p)` even when more data is coming and `err == nil`. Never assume one `Read` call fills your buffer — loop, or use a helper that loops for you.
3. **`io.EOF` is not a failure.** It is the normal signal that there is no more data. Treat `err == io.EOF` as "stop looping, no error to report" — never `log.Fatal` it or return it up the stack unwrapped as if something broke.

```go
n, err := r.Read(buf)
if n > 0 {
    process(buf[:n]) // always handle n bytes first
}
if err != nil {
    if err == io.EOF {
        return nil // clean end of stream, not an error
    }
    return err
}
```

When you need an exact or minimum number of bytes and don't want to hand-write the loop, `io.ReadFull(r, buf)` reads until `buf` is full or returns `io.ErrUnexpectedEOF` if the stream ends first; `io.ReadAtLeast(r, buf, min)` is the same idea for a minimum length instead of the full buffer.

## bufio.Scanner's 64 KB token limit

`bufio.Scanner` caps each token (line) at `bufio.MaxScanTokenSize` — 64 KB — by default. When a line exceeds that, `Scan()` returns `false` and `Err()` returns `bufio.ErrTooLong`. This looks exactly like clean EOF unless you check `Err()` after the loop — the rest of the input is silently dropped.

```go
scanner := bufio.NewScanner(r)
scanner.Buffer(make([]byte, 0, 64*1024), 1024*1024) // raise the max to 1 MB
for scanner.Scan() {
    process(scanner.Text())
}
if err := scanner.Err(); err != nil {
    log.Fatal(err) // catches ErrTooLong, not just I/O errors
}
```

`scanner.Buffer(initial, max)` sets both the starting buffer and the ceiling it is allowed to grow to. Call it before the first `Scan()` if a single line might legitimately exceed 64 KB (a long JSON line, a base64 blob).

## bufio.Writer, Flush, and Close errors

`bufio.Writer` buffers writes in memory and only reaches the underlying `io.Writer` when the buffer fills, or when you call `Flush()` explicitly. Nothing is guaranteed to have reached disk or the network until `Flush()` returns.

A `Close()` error matters for the same reason: a type built on top of a buffered writer (or a file) can surface a delayed write failure — such as a disk-full error — only when the last flush happens inside `Close`. Ignoring `defer f.Close()`'s return value silently swallows that failure.

```go
w := bufio.NewWriter(f)
fmt.Fprintln(w, "important data")
if err := w.Flush(); err != nil {
    return fmt.Errorf("flush: %w", err) // the write may not have failed until now
}
if err := f.Close(); err != nil {
    return fmt.Errorf("close: %w", err) // a writer's Close error is not decorative
}
```

## io.Copy, TeeReader, Pipe, and NopCloser

`io.Copy(dst, src)` reads from `src` and writes to `dst` until `src` returns `io.EOF`, relying on the `Writer` contract: `Write` must return a non-nil error if it wrote fewer than `len(p)` bytes, so `io.Copy` can trust a `nil` error to mean the full chunk landed.

Three small `io` helpers round out the toolkit:

- **`io.TeeReader(r, w)`** — returns a Reader that mirrors every byte it reads into `w` as a side effect (checksumming or logging a stream while it is consumed, without buffering it all in memory first).
- **`io.Pipe()`** — an in-memory, synchronous `io.Reader`/`io.Writer` pair with no buffer; a write blocks until a matching read drains it, useful for streaming data from one goroutine to another without an intermediate buffer.
- **`io.NopCloser(r)`** — wraps an `io.Reader` with a no-op `Close`, satisfying `io.ReadCloser`. This is exactly what `http.Request.Body` needs in a test, or what you hand back when you don't want a caller to close a shared reader.

```go
tee := io.TeeReader(resp.Body, hasher)     // reading tee also feeds hasher
req.Body = io.NopCloser(bytes.NewReader(replayed)) // satisfy io.ReadCloser in a test
```

## bytes.Buffer must not be copied

`bytes.Buffer` holds its data in an internal slice; copying a `bytes.Buffer` by value (assigning it, passing it by value, or storing it in a slice you then append to) copies that slice header without copying a mutex or lock — but the two copies now alias the same backing array while each tracks its own read/write offsets independently, so writes and reads on one copy corrupt what the other sees. The package doc says so explicitly: *"The zero value for Buffer is an empty buffer ready to use... Do not copy a non-zero Buffer."*

Unlike `sync.Mutex`, there is no `go vet copylocks`-style check for this — `bytes.Buffer` does not embed a `noCopy` marker, so the compiler and `go vet` stay silent. Always pass `*bytes.Buffer`, never `bytes.Buffer` by value, once it holds data.

## Mental Model

```text
io.Reader interface:
  Source → [Read(p []byte)] → buffer p → consumer

Chaining readers:
  os.File → bufio.NewReader → gzip.NewReader → json.NewDecoder
  ↓          ↓                ↓                ↓
  raw        buffered         decompressed     decoded

bufio.Writer batching:
  small writes → [buffer 4 KB] → one flush → os.File
  many syscalls                  one syscall
```

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| bufio.Reader | Fewer syscalls (batches reads) | Extra memory for the buffer |
| bufio.Writer | Fewer syscalls (batches writes) | Must call Flush() before close |
| io.Reader chain | Composable, zero-copy pipeline | Error handling gets complex when the chain is long |
| io.Copy | Efficient transfer between Reader and Writer | Cannot inspect the data in transit |

## Common Misconceptions

- **An unbuffered read is fast enough** — every `Read()` call with no buffer is one syscall — very slow for many small reads.
- **bufio.Writer flushes automatically** — it does not; you must call `Flush()` yourself before closing or sending the response, or the data can be lost.
- **io.Reader always reads exactly n bytes** — `Read()` may return fewer than `n` bytes; loop until you have what you need when you require an exact read.
- **strings.NewReader and bytes.NewReader are the same** — `strings.NewReader` is for a string literal; `bytes.NewReader` is for a `[]byte` you already have.

> 💡 Real-world example
>
> **Go HTTP servers**: `net/http` automatically wraps the TCP connection in a `bufio.Reader` — request parsing does not need a syscall per byte.

<Callout title="Program to io.Reader and io.Writer, not to concrete types">
Write your functions to accept `io.Reader` or `io.Writer` rather than `*os.File` or `*http.Request`. This single habit makes your code universally testable — pass a `strings.NewReader` in tests, a real file in production, and an HTTP body in handlers, all without touching the function. It also means your function participates in the entire ecosystem of Go I/O composition: `bufio.NewReader`, `io.MultiReader`, `io.LimitReader`, `gzip.NewReader`, and so on.
</Callout>

## Reading AI-generated code

AI assistants write `io`/`bufio` code that compiles and looks reasonable far more often than code that is actually correct on the edges. Check for these before trusting a review:

- Does a `bufio.Scanner` loop check `scanner.Err()` after the loop, or does it treat `false` as always meaning clean EOF?
- If the input could contain a line longer than 64 KB, did it call `scanner.Buffer(...)` to raise the limit, or will it silently truncate?
- Does anything written through a `bufio.Writer` get `Flush()`ed before the function returns or the response is sent?
- Is `f.Close()`'s return value checked when `f` was written to, not just when it was read from?
- Does a custom `Read` implementation assume the caller always gets a full buffer, or does the caller correctly loop / use `io.ReadFull`?
- Is a `bytes.Buffer` ever copied by value (passed as an argument, stored in a slice, returned from a function) after it has data in it?

	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()

	cfg := map[string]string{}
	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		k, v, _ := strings.Cut(scanner.Text(), "=")
		cfg[k] = v
	}
	return cfg, nil
}`}>

The loop never checks `scanner.Err()`. If one line in `path` is longer than the default 64 KB limit — a long value, a stray binary file — `Scan()` returns `false`, the loop ends, and `loadConfig` returns a **partial** config with a `nil` error, as if the file had been read completely. Fix it by checking the error after the loop:

```go
if err := scanner.Err(); err != nil {
    return nil, fmt.Errorf("scan %s: %w", path, err)
}
return cfg, nil
```

If lines longer than 64 KB are expected and valid, call `scanner.Buffer(make([]byte, 0, 64*1024), maxLineSize)` before the loop instead of just detecting the failure.
