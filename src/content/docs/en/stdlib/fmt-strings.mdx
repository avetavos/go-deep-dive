## fmt — formatted I/O

The `fmt` package is the entry point for almost all output in Go. Three functions cover the vast majority of use cases:

- `fmt.Println(args...)` — prints each argument separated by spaces, followed by a newline.
- `fmt.Printf(format, args...)` — prints using a format string with verbs.
- `fmt.Sprintf(format, args...)` — returns the formatted string instead of printing it.

### Format verbs

| Verb | Meaning |
|------|---------|
| `%v` | Default representation |
| `%+v` | Struct with field names |
| `%#v` | Go-syntax representation |
| `%T` | Type of the value |
| `%d` | Decimal integer |
| `%s` | String (unquoted) |
| `%q` | Double-quoted string with Go escaping |
| `%f` | Floating-point decimal |

```go
type Person struct { Name string; Age int }
p := Person{"Alice", 30}
fmt.Printf("%v\n",  p)   // {Alice 30}
fmt.Printf("%+v\n", p)   // {Name:Alice Age:30}
fmt.Printf("%#v\n", p)   // main.Person{Name:"Alice", Age:30}
fmt.Printf("%T\n",  p)   // main.Person
```

### %v calls String() — and can recurse into it

When a value implements `fmt.Stringer` (`String() string`) or `error`, `%v` (and `%s`, `Println`, and every verb that falls back to the default representation) calls that method instead of printing the struct's fields. This is convenient — until the `String()` method itself formats the receiver with `%v`:

```go
type Point struct{ X, Y int }

func (p Point) String() string {
    return fmt.Sprintf("%v", p) // BUG: %v on a Stringer calls String() again
}
```

`go vet` catches this specific shape at compile time — it is common enough in AI-generated code to have its own analyzer:

```text
main.go:8:22: fmt.Sprintf format %v with arg p causes recursive (command-line-arguments.Point).String method call
```

The fix is to format the underlying fields, or a converted type that does not carry the method: `fmt.Sprintf("(%d, %d)", p.X, p.Y)`, or `fmt.Sprintf("%v", struct{ X, Y int }(p))`.

### Width and padding verbs

Every verb accepts a width and, for floats, a precision, written before the verb letter:

```go
fmt.Printf("%08b\n", 5)      // 00000101 — zero-padded to 8 digits
fmt.Printf("[%6.2f]\n", 3.14159) // [  3.14] — width 6, 2 decimal places
fmt.Printf("%x\n", 255)      // ff — lowercase hex
```

A negative width left-aligns instead of right-aligning (`%-8s`); the same width syntax works for `%d`, `%s`, `%q`, and every other verb.

## %w is only valid inside fmt.Errorf

`%w` is not a general formatting verb — it is a signal to `fmt.Errorf` specifically, telling it to wrap the given error so `errors.Is`/`errors.As`/`errors.Unwrap` can see through it later. Every other `fmt` function treats `%w` as an error and refuses to compile with `go vet`:

```go
baseErr := errors.New("disk full")
wrapped := fmt.Errorf("save failed: %w", baseErr) // OK — Errorf understands %w
```

```go
notWrapped := fmt.Sprintf("save failed: %w", baseErr) // go vet error
```

```text
main.go:17:42: fmt.Sprintf does not support error-wrapping directive %w
```

`go vet` (part of `go build`'s default checks since Go 1.10 for a subset of analyzers, and always run by `go test`) rejects this at compile-check time, so the mistake rarely reaches production — but it is worth recognising when reading a diff, because AI-generated code sometimes copies a `%w`-bearing format string into a `Sprintf` or `Println` call by habit.

## strings — text manipulation

The `strings` package provides functions for searching, splitting, joining, and transforming strings. Strings in Go are immutable UTF-8 byte sequences; these functions return new strings rather than modifying in place.

```go
s := "hello, world"
strings.Contains(s, "world")         // true
strings.HasPrefix(s, "hello")        // true
strings.Split(s, ", ")               // ["hello" "world"]
strings.Join([]string{"a","b"}, "-") // "a-b"
strings.ReplaceAll(s, "l", "L")      // "heLLo, worLd"
strings.ToUpper(s)                   // "HELLO, WORLD"
strings.TrimSpace("  hi  ")          // "hi"
```

### Strings are bytes; range walks runes

A Go string is an immutable sequence of bytes, usually holding UTF-8 text. `len(s)` counts **bytes**, and `s[i]` indexes a single **byte** — not a character. `for range` over a string, by contrast, decodes UTF-8 and gives you the **rune** (a Unicode code point, `int32`) at each position, together with the byte offset it started at:

```go
s := "café" // é is 2 bytes in UTF-8
fmt.Println(len(s), utf8.RuneCountInString(s)) // 5 4 — byte count vs rune count differ
for i, r := range s {
    fmt.Printf("byte %d: rune %q\n", i, r)
}
fmt.Println(s[3]) // 195 — a raw UTF-8 continuation byte, not a printable rune
```

Indexing `s[i]` with an arithmetic offset (rather than iterating with `range` or converting to `[]rune`) is only safe for pure-ASCII strings; any non-ASCII input silently slices into the middle of a multi-byte character.

### TrimPrefix vs TrimLeft: the cutset trap

`strings.TrimPrefix(s, prefix)` removes `prefix` only if `s` starts with that exact string, once. `strings.TrimLeft(s, cutset)` looks completely different: it treats `cutset` as a **set of individual bytes**, and strips every leading byte that appears anywhere in that set — not a prefix string:

```go
strings.TrimPrefix("aardvark", "ar") // "aardvark" — does not start with "ar"
strings.TrimLeft("aardvark", "ar")   // "dvark"    — strips every leading 'a' or 'r'
```

AI-generated code that reaches for `TrimLeft` expecting prefix-string behaviour produces a plausible-looking but wrong result on any input where the cutset characters repeat or appear in the wrong order — use `TrimPrefix` (or `CutPrefix`) whenever the intent is "remove this exact prefix."

### strings.Builder — efficient concatenation

When building a string from many pieces in a loop, use `strings.Builder` instead of `+=`. The `+=` operator allocates a new string on every iteration; `Builder` writes into a growing buffer and only allocates the final string once.

```go
var b strings.Builder
b.Grow(64) // pre-size the buffer when you know roughly how much you'll write
for i := 0; i < 5; i++ {
    fmt.Fprintf(&b, "item%d ", i)
}
result := strings.TrimSpace(b.String()) // "item0 item1 item2 item3 item4"
```

`Builder` is not safe to copy once it holds data — like `bytes.Buffer`, but `strings.Builder` actively enforces it. Copying a non-zero `Builder` by value and then writing to the copy panics at runtime with `strings: illegal use of non-zero Builder copied by value`, because the copy carries a pointer back to the original's buffer that the runtime detects has moved.

### Cut, CutLast, and iterator helpers

Three families of helpers arrived in recent releases and replace a lot of index arithmetic:

```go
// Go 1.18: split on the FIRST separator
key, val, ok := strings.Cut("user=alice", "=")      // "user", "alice", true

// Go 1.27: split on the LAST separator — replaces strings.LastIndex dances
dir, file, ok := strings.CutLast("a/b/c.txt", "/") // "a/b", "c.txt", true

// Go 1.24: lazy iterators — no intermediate []string allocation
text := "a=1\nb=2\n"
for line := range strings.Lines(text) { fmt.Print(line) }              // keeps the "\n"
for part := range strings.SplitSeq("a,b,c", ",") { fmt.Println(part) }
for word := range strings.FieldsSeq("  a  b ") { fmt.Println(word) }
```

`Lines`, `SplitSeq`, and `FieldsSeq` return `iter.Seq[string]`; use them when you only need to walk the pieces once, and keep `Split`/`Fields` when you need a slice you index into. `bytes` has the same set (`bytes.CutLast` and friends).

Two other small additions worth knowing: the new `uuid` package (Go 1.27) generates and parses UUIDs without a third-party module, and `log/slog.NewMultiHandler` (Go 1.26) fans one logger out to several handlers.

## strconv — string-to-number conversions

`strconv` converts between strings and numeric types. The most common functions:

```go
n, err   := strconv.Atoi("42")          // string → int
s        := strconv.Itoa(42)            // int → string
f, err   := strconv.ParseFloat("3.14", 64) // string → float64
b, err   := strconv.ParseBool("true")   // string → bool
```

`Atoi` and `ParseFloat` return `(value, error)` because the input might not be a valid number. Always check the error before using the value.

`ParseInt(s, base, bitSize)` handles other bases (`strconv.ParseInt("2A", 16, 64)` → `42`), and `strconv.Quote` produces a Go-syntax-quoted string with escapes made visible — useful for logging a value that might contain control characters.

### strconv vs fmt.Sprint for numbers

`strconv.Itoa(n)` and `fmt.Sprint(n)` produce the same string for an int, but they are not equally cheap. `fmt.Sprint` boxes its argument into an `any`, then uses reflection to discover it is an integer before formatting it; `strconv.Itoa` converts directly with no boxing or reflection. Benchmarked on this machine:

```text
BenchmarkItoa-11      92186020    12.60 ns/op    8 B/op    1 allocs/op
BenchmarkSprint-11    35726424    34.59 ns/op    8 B/op    1 allocs/op
```

Same allocation count, but `fmt.Sprint` costs roughly 2.7x more CPU time per call — reflection is not free even when it does not allocate more. Prefer `strconv` in a hot path where you know the concrete type; reach for `fmt.Sprintf` when you need to interpolate several values into a template.

## Trade-offs

| What you get | Benefit | Cost |
|---------|---------|------|
| fmt.Sprintf | Flexible string formatting | Allocates a new string every call |
| fmt.Fprintf(w, ...) | Write to any io.Writer | You must check the returned error |
| strings.Builder | Efficient string concatenation | Must call Reset() before reuse |
| %v / %+v / %#v | Inspect any value | Reflection-based — slower than an explicit conversion |

## Common Misconceptions

- **fmt.Println is fine for production logging** — use a structured logger (`log/slog`, zap) in production instead; `fmt` has no log levels, structured fields, or JSON output.
- **String concatenation with + is faster than fmt.Sprintf** — it depends on how many concatenations there are; `strings.Builder` is fastest for many pieces in a loop.
- **%d and %v are very different** — `%d` is explicit for integers, `%v` is generic but produces the same output for an int; they differ for structs.
- **rune and byte are the same thing** — a `byte` is a `uint8` (1 byte); a `rune` is an `int32` (1-4 bytes for a Unicode code point).
- **TrimLeft(s, "prefix") removes the prefix "prefix"** — it removes leading bytes found anywhere in the cutset, not a prefix string; use `TrimPrefix` for that.
- **%w works anywhere you'd use %v for an error** — `%w` is meaningful only inside `fmt.Errorf`; every other `fmt` function rejects it at `go vet` time.

> 💡 Real-world example
>
> **kubectl** formats table output with `fmt.Fprintf` and `text/tabwriter`, which aligns columns automatically.
>
> **Go HTTP servers** build an error message with `fmt.Sprintf` and pass it to `http.Error`, which accepts a plain string.

<Callout title="%+v and %#v are your debugging friends">
When you are unsure what is inside a struct, reach for `%+v` first — it prints field names alongside values so you can immediately see which field holds which data. Use `%#v` when you want a copy-pasteable Go literal (useful for writing test fixtures). For production logs, prefer structured logging (`log/slog`) over `fmt.Printf`, but in development and tests `%+v` saves a lot of time.
</Callout>

## Reading AI-generated code

`fmt`/`strings`/`strconv` code compiles almost regardless of whether it is correct, which makes it easy to skim past a subtle bug. Check for these:

- Does a `String()` method format the receiver with `%v` (or `%s`, or `fmt.Sprint`) instead of its individual fields — a recursion `go vet` flags but is easy to miss in review?
- Does `%w` appear in any `fmt` call other than `Errorf`? It is a silent no-op error there that `go vet` also catches, but only if it runs.
- Does code call `strings.TrimLeft`/`TrimRight` expecting prefix/suffix-string removal? Those take a cutset of bytes, not a substring — `TrimPrefix`/`TrimSuffix` are what "remove this exact string" means.
- Does code index a string by byte offset (`s[i]`, `s[i:j]`) when the input might contain non-ASCII text? That can slice into the middle of a multi-byte rune.
- Is `strconv` skipped in favour of `fmt.Sprintf`/`fmt.Sprint` for a simple number-to-string conversion in a hot path, paying for reflection that buys nothing?
- Is a `strings.Builder` (or `bytes.Buffer`) copied by value after it has been written to, instead of passed by pointer?
