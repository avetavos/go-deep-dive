## What this module is for

Every earlier module in this course taught you to *write* Go: syntax, types, methods, concurrency primitives, the standard library. None of it required you to know how any of it actually runs. You can write a working goroutine, a correct `sync.Mutex`, a struct with a dozen fields, without ever asking what the scheduler does with the first, what "correct" even means for the second, or how the third is arranged in memory.

That gap is exactly where AI-generated Go fails most often — and where a reviewer who has never seen the machinery underneath fails to catch it. A generated snippet can be syntactically perfect, pass `go vet`, and still leak a goroutine, race on a shared flag, or allocate on every call in a hot loop. None of those are syntax errors. All three are runtime facts.

This module has one job: give you the four pieces of runtime knowledge that let you look at **someone else's Go source** — not run it, not profile it, just read it — and answer three questions with confidence:

1. **Does this allocate?** (escape analysis, memory layout)
2. **Can this race?** (the memory model, happens-before)
3. **Can this leak or block forever?** (the scheduler, goroutine lifecycle)

## A runnable question: what does the runtime already know about your program?

Before any of the deeper mechanism, the `runtime` package itself answers simple version of all three questions from inside a running program — no profiler needed.

export const runtimeSurveyCode = `package main

import (
\t"fmt"
\t"runtime"
\t"sync"
)

func main() {
\tfmt.Println("Go version:", runtime.Version())
\tfmt.Println("GOARCH/GOOS:", runtime.GOARCH, runtime.GOOS)
\tfmt.Println("NumCPU:", runtime.NumCPU())
\tfmt.Println("GOMAXPROCS:", runtime.GOMAXPROCS(0))
\tfmt.Println("goroutines before:", runtime.NumGoroutine())

\tvar wg sync.WaitGroup
\tblock := make(chan struct{})
\tfor i := 0; i < 3; i++ {
\t\twg.Add(1)
\t\tgo func() {
\t\t\tdefer wg.Done()
\t\t\t<-block // parked, not spinning on CPU
\t\t}()
\t}
\tfmt.Println("goroutines after launch:", runtime.NumGoroutine())
\tclose(block)
\twg.Wait()
\tfmt.Println("goroutines after Wait:", runtime.NumGoroutine())
}`;

<Playground code={runtimeSurveyCode} />

Real output on darwin/arm64, 11 logical CPUs:

```text
Go version: go1.27.0
GOARCH/GOOS: arm64 darwin
NumCPU: 11
GOMAXPROCS: 11
goroutines before: 1
goroutines after launch: 4
goroutines after Wait: 1
```

`runtime.NumGoroutine()` counting 4 after launching 3 (the main goroutine plus three parked ones) and dropping back to 1 after `wg.Wait()` is the cheapest leak check that exists: snapshot the count before and after a piece of code runs, and assert it returns to baseline. You will use exactly this trick again in the Scheduler lesson.

## Mental Model

```text
Your only view of unfamiliar Go:        What actually decides behavior:

  source code                            memory model (happens-before)
      │  "does this look right?"              │ is this write visible elsewhere?
      ▼                                        ▼
  compiles, vets clean         ──────►    scheduler (GMP)
      │                                        │ does this goroutine ever run again?
      ▼                                        ▼
  "looks idiomatic"                        GC + escape analysis
                                                │ does this allocate, and when is it freed?
                                                ▼
                                          memory layout
                                                │ how many bytes, how aligned?
```

Reading Go well means running this right-hand column in your head while your eyes are only doing the left-hand one.

## Trade-offs

| What you get | Benefit | Cost |
|---|---|---|
| Knowing the memory model | You can spot a race without running `-race` | It takes real study — happens-before is not "same line order" |
| Knowing the scheduler | You can predict when a goroutine blocks vs. leaks | GMP has real depth (local/global queues, netpoller, sysmon) |
| Knowing escape analysis | You can predict allocations by reading, not just benchmarking | The compiler's actual reasoning changes across Go releases |
| Knowing memory layout | You can spot wasteful struct padding on sight | Only matters at scale — premature layout tuning wastes readability |

## Common Misconceptions

- **"It compiled and `go vet` passed, so it's fine"** — `go vet` and the compiler check syntax and a fixed set of known mistakes; they do not check whether your program races, leaks a goroutine, or allocates needlessly. All three compile cleanly.
- **"Runtime internals are for people writing the Go compiler"** — you need enough of this to *read*, not to reimplement the scheduler. Every fact in this module is something you can point to in someone else's diff.
- **"The race detector always tells you if code is safe"** — it only reports races that actually happen during the run it instruments; a code path a test never exercises can still race in production. The Memory Model lesson covers exactly what `-race` does and does not catch.
- **"Profiling is the only way to know if something allocates"** — profiling confirms; reading `-gcflags='-m -m'` output or knowing the four or five shapes that force an escape lets you predict it from the source, which is the point of this module.

<Callout title="This module trades breadth for the reading skill, not exhaustive runtime coverage">
None of these four lessons make you able to reimplement the Go runtime — they are deliberately scoped to the facts that change how you read a diff: what forces a heap allocation, what a data race actually is, why a goroutine is stuck, and what a struct actually costs in bytes. Anything deeper (runtime source code, GC algorithm internals beyond what changes your reading) is out of scope on purpose.
</Callout>

## Reading AI-generated code

The whole point of this module is this section, four times over — one per lesson. As a preview, here is the survey-level version: a snippet that compiles, passes `go vet`, and is still wrong in a way none of the earlier modules in this course would catch.

<SpotTheBug code={`func recordHit(counts map[string]int, key string) {
	go func() {
		counts[key]++ // no lock, no channel, called from many goroutines
	}()
}`}>
This compiles. It passes `go vet`. Nothing in the Basics, Types, or Methods modules flags it. But `counts[key]++` from an unsynchronized goroutine, called concurrently from more than one place, is a **data race** on a plain Go `map` — which is not even safe for *one* writer plus any reader at the same time, let alone two writers. Two goroutines can genuinely corrupt the map's internal structure, and Go's runtime detects this specific case and crashes with `fatal error: concurrent map writes` rather than silently corrupting data — but only if you get lucky enough to trigger the runtime's own check. The Memory Model lesson in this module explains exactly why "no shared mutable state" has to be enforced by you, not inferred from the code compiling.

```go
func recordHit(mu *sync.Mutex, counts map[string]int, key string) {
	mu.Lock()
	defer mu.Unlock()
	counts[key]++
}
```
</SpotTheBug>
